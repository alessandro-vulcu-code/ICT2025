## Study Notes

### The Raw Pointer Problem

Raw pointers are sometimes used when an object must survive beyond the scope in which it was created, for example when passing data between functions, threads, or object hierarchies. A common old-style solution is to allocate the object on the heap with `new`.

The problem is that every `new` must be paired with a corresponding `delete`. This creates an ownership question: **who is responsible for deleting the object?** If the answer is unclear, the program can leak memory, delete an object too early, or access memory after the object has been destroyed.

#### Dangling Pointers

A **dangling pointer** is a pointer that still stores an address after the object at that address has already been destroyed. Dereferencing it gives **undefined behavior**.

```cpp
char* buffer = new char [256];
delete []buffer;
std::cout << *buffer
```

This code deletes the array and then dereferences `buffer`. The pointer value still exists, but it no longer points to a valid object. The source also omits a final semicolon after the `std::cout` line.

```cpp
char* buffer = new char [256];
delete []buffer; // now buffer is dangling
buffer = null; // now it is not dangling anymore
```

The intended modern C++ spelling is `nullptr`, not `null`. Setting the pointer to `nullptr` avoids accidentally dereferencing the old address, but it does not solve ownership management by itself.

#### Leaks and Early Exits

Raw pointer code is fragile when a function has exceptions or early returns.

```c
int performTask() {
    char* buffer = new char [256];

    ...
    ... // Some code here
    ... // of several lines
    ... // that may trow exception
    ... // or return something
    ... // before the end is reached
    ...
    delete []buffer;
    return 0;
}
```

If execution leaves the function before `delete []buffer`, the allocated memory is leaked. The source writes `trow`; the intended word is likely `throw`.

```c
int performTask() {
    char* buffer = new char [256];
    ...
    ...
    ...
    if(<some_condition>) {
        return 1;
    }
    delete []buffer;
    return 0;
}
```

This version leaks when `<some_condition>` is true, because the function returns before deleting the buffer.

```c
int performTask() {
    char* buffer = new char [256];

    ...
    ...
    ...
    if(<some_condition>) {
        delete []buffer;
        return 1;
    }
    delete []buffer;
    return 0;
}
```

This manually handles the early return, but the approach does not scale. Every new return path or exception path must remember to release the resource.

### RAII and Smart Pointers

The manual solution is to put `delete[]` before every possible exit and use `try`/`catch` for exceptions. This is verbose and easy to break during maintenance.

The C++ solution is **RAII**: Resource Acquisition Is Initialization. A wrapper object acquires the resource in its constructor and releases it in its destructor. When the wrapper goes out of scope, cleanup happens automatically.

The Standard Library provides smart pointers in `<memory>`:

- **`std::unique_ptr`** for exclusive ownership;
- **`std::shared_ptr`** for shared ownership;
- **`std::weak_ptr`** for non-owning observation of an object managed by `shared_ptr`.

With `unique_ptr` and `shared_ptr`, use `operator->` to access members of the pointed object.

### Unique Pointer

`std::unique_ptr` is a **scoped pointer** with exclusive ownership. It owns one dynamically allocated object and deletes it automatically when the `unique_ptr` is destroyed, reset, or moved from.

```cpp
std::unique_ptr<string> up(new std::string("ciao"));
```

This wraps a raw pointer in a `unique_ptr`. In modern code, prefer `std::make_unique<std::string>("ciao")` when available, but the slide shows direct construction from `new`.

A `unique_ptr` is **lightweight** and cannot be copied. There can be only one owner at a time.

#### Ownership Transfer

```cpp
std::unique_ptr<string> up2 = up; // not allowed!!
std::unique_ptr<string> up2 = std::move(up); // up releases ownership...
```

The first line is invalid because copying a `unique_ptr` would create two owners. The second line moves ownership from `up` to `up2`; after the move, `up` no longer owns the object.

```cpp
void function f1(std::unique_ptr<T1> up) {
    //do stuff
}

std::unique_ptr<T1> up1 (new T1 ());
f1(up1); // not allowed!!

f1(std::move(up1)); // IT WORKS, BUT BE AWARE THE OBJECT IS DESTROYED INSIDE THE FUNCTION f1!!!
```

The function declaration is malformed in the source; the likely intended form is `void f1(std::unique_ptr<T1> up)`. Passing by value transfers ownership into the function, so the object is destroyed when the local parameter `up` goes out of scope unless ownership is returned or moved elsewhere.

#### Passing Unique Pointers

One solution is to pass ownership into a function and return it:

```cpp
std::unique_ptr<T1> f1(
    std::unique_ptr<T1> up) {
    //do stuff with up
    return up; // returns it by move
}

std::unique_ptr<T1> up1(new T1());
up1 = f1(std::move(up1));
```

This makes ownership transfer explicit: `up1` is moved into the function and then receives ownership back from the return value.

Another solution is to pass the `unique_ptr` by const reference when the function only needs to inspect or use the object without taking ownership:

```cpp
void f2(
    const std::unique_ptr<T1>& up) {
    //do stuff with up
}

std::unique_ptr<T1> up1(new T1());
f2(up1);
```

This does not transfer ownership. In many designs, passing `T1&` or `const T1&` may be even clearer if the function does not need to know that the object is owned by a `unique_ptr`.

#### Useful Operations

Useful `unique_ptr` operations include:

- `release()`, which returns the raw pointer and makes the `unique_ptr` empty;
- `reset()`, which destroys the currently owned object;
- `reset(new T(...))`, which destroys the old object and takes ownership of a new one.

```cpp
string* s = up.release();
```

After `release()`, `up` no longer owns the object. The caller must either delete the raw pointer manually or immediately transfer it to another owner.

```cpp
up.reset();
```

This destroys the currently owned object and leaves `up` empty.

```cpp
up.reset(new string("hi"));
```

This destroys the old owned object, if any, and makes `up` own the new string.

### Shared Pointer

`std::shared_ptr` represents **shared ownership**. Several `shared_ptr` objects can refer to the same object. The object is destroyed only when the last owning `shared_ptr` is destroyed or reset.

```cpp
std::shared_ptr<string> sp(new string("ciao")); // *use_count = 1
```

This creates a shared owner for a dynamically allocated string. The `use_count` is the number of `shared_ptr` instances that currently share ownership.

#### Reference Counting

```cpp
std::shared_ptr<string> sp2 = sp; // *use_count=2
```

Copying a `shared_ptr` increases the reference count. Each owner contributes to keeping the object alive.

Conceptually, destruction works like this:

```cpp
(*use_count)--;
if (*use_count <= 0) {
    delete p;
}
```

The source slide uses a non-ASCII less-than-or-equal symbol. The real implementation is more complex, but the exam idea is that the object is deleted when the count reaches zero.

```cpp
int fun1(shared_ptr<T1> sp) { //*use_count=3
  sp... //DO STUFF
  return 0;
} //sp goes out of scope: *use_count=2

main() {
  shared_ptr<T1> sp1 =
    make_shared <T>(val); // *use_count = 1

  auto sp2 = sp1; // *use_count = 2
  int x = fun1(sp1);
} // sp1 and sp2 go out of scope:
// *use count = 0, pointed object is
// destroyed
```

This example shows how copies increase and decrease the reference count. The source omits `std::` qualifiers, omits the return type for `main`, and writes `T` where `T1` is probably intended. The ownership concept remains the same.

#### Make Shared and Utilities

The preferred way to create a `shared_ptr` is usually `std::make_shared`:

```cpp
std::shared_ptr<string> sp = std::make_shared<string>("s");
```

`make_shared` is concise and exception-safe. It also typically performs one allocation for the object and its control block.

Useful operations include:

- `sp.use_count()`, which returns the current number of shared owners;
- `sp.reset()`, which releases this owner's share;
- `sp.get()`, which returns the raw pointer without transferring ownership.

The source writes `sp.use_reset()`, which appears to be a typo for `sp.reset()`.

```cpp
string* p = sp.get();
```

`get()` is useful for interoperability with APIs that need a raw pointer, but the returned pointer must not be deleted manually. Ownership remains with the `shared_ptr`.

`shared_ptr` can also use a custom deleter, although the course material focuses on the default deleter.

#### Pointer Casts

The Standard Library provides casts that preserve shared ownership:

- `std::dynamic_pointer_cast<D>(s_ptr)`;
- `std::static_pointer_cast<D>(s_ptr)`;
- `std::const_pointer_cast<const D>(s_ptr)`.

```cpp
std::shared_ptr<B> pb = std::make_shared<D>();
std::shared_ptr<D> pd1 =
std::dynamic_pointer_cast<D>(pb);
if(pd1 != nullptr) {...}
std::shared_ptr<D> pd2 =
std::static_pointer_cast<D>(pb);
std::shared_ptr<const D> c_pd =
std::const_pointer_cast<const D>(pb);
```

`dynamic_pointer_cast` performs a checked downcast and may return an empty `shared_ptr`. `static_pointer_cast` relies on the programmer's type knowledge. `const_pointer_cast` changes const qualification. The source uses a non-C++ not-equal symbol; the intended operator is `!=`.

### Weak Pointer

`std::weak_ptr` is a **non-owning** reference to an object managed by `std::shared_ptr`. It observes the object without increasing the shared reference count.

This is useful when one object needs to refer to another but must not extend its lifetime.

#### Circular References

Using only `shared_ptr` can create cycles:

```c
struct Son{
    shared_ptr<Mum> mum
};
struct Mum{
    shared_ptr<Son> son
};
main() {
    shared_ptr<Son> son1 =
        make_shared <Son>();
    shared_ptr<Mum> mum1 =
        make_shared <Mum>();
    son1->mum = mum1; // obj2 use_count = 2
    mum1->son = son1; // obj1 use_count = 2
} CYCLIC REFERENCE -> MEMORY LEAK!!
NONE OF THE SHARED PTR GOES OUT OF SCOPE
```

This code is syntactically incomplete: it lacks semicolons, `std::` qualifiers, and a proper `main` signature. Conceptually, each object keeps the other alive through a `shared_ptr`, so neither reference count reaches zero.

The cycle is broken by replacing at least one owning relationship with `weak_ptr`:

```c
struct Son{
    weak_ptr<Mum> mum
};
struct Mum{
    weak_ptr<Son> son
};
main() {
    shared_ptr<Son> son1 =
        make_shared <Son>();
    shared_ptr<Mum> mum1 =
        make_shared <Mum>();
    son1->mum = mum1; // obj2 use_count = 1
    mum1->son = son1; // obj1 use_count = 1
} NOW THEY ARE CORRECTLY DESTROYED
```

Here the cross-references do not increase `use_count`, so the objects are destroyed when the external `shared_ptr` variables go out of scope.

#### Using lock

The source introduces `weak_ptr` from a `shared_ptr`:

```c
shared_ptr<T1> sp = make_shared<T1>();
weak_ptr<T1> wp1 = sp1;
```

The second line likely intends `weak_ptr<T1> wp1 = sp;`, because the previous variable is named `sp`.

A `weak_ptr` cannot be dereferenced directly with `->`. First call `lock()`, which returns a `shared_ptr` if the object is still alive or an empty `shared_ptr` if it has expired.

```cpp
if (auto tmp_sp = wp.lock()) { // it checks if tmp_sp is not empty
    tmp_sp->getParam();
} // the shared pointer tmp_sp goes out of scope

use_count() checks how many shared pointer points to that object

expired() checks if use_count() = 0
```

The source labels this block as JavaScript and uses a corrupted arrow. The intended C++ access is `tmp_sp->getParam();`. The important idea is that `lock()` temporarily promotes a `weak_ptr` into a `shared_ptr`, keeping the object alive during use.

### Wrong Uses of Smart Pointers

Do not create multiple independent smart pointers from the same raw pointer.

```cpp
string* p = new string("ciao");
std::shared_ptr<string> sp(p); // count = 1
std::shared_ptr<string> sp2(p); // count = 1

// Who is responsible of deleting the object?

// To avoid this problem follow this rule:
// An object should be assigned to a smart pointer as soon as it is created

std::shared_ptr<string> sp1 =
    std::make_shared<string>("ciao");
```

`sp` and `sp2` have separate control blocks, so each believes it is the unique owner. This can lead to double deletion. The rule is: **put a newly created object into a smart pointer immediately**, and prefer `make_unique` or `make_shared`.

## Final Summary

Raw pointers make ownership and lifetime management fragile, especially with early returns, exceptions, and shared object graphs. **RAII** solves this by tying resource lifetime to object lifetime. Use `std::unique_ptr` for exclusive ownership, `std::shared_ptr` when ownership is genuinely shared, and `std::weak_ptr` to observe shared objects without extending their lifetime. The main exam point is not just knowing the classes, but explaining which pointer expresses the ownership model correctly.
