## Study Notes

This lesson follows **[c++pl] Chapter 17** and explains the C++ object life cycle: construction, cleanup, copy, move, default operations, and deleted functions.

### Object Life Cycle

An object is first **constructed**, then it can go through operations during its lifetime, and finally it is **destroyed**. These operations are related: if a type owns resources, construction, destruction, copy, and move must all preserve correct ownership.

Many life-cycle operations can be automatically generated by the compiler, but the generated behavior is only correct when member-wise behavior matches the class semantics.

#### Life-Cycle Operations

The complete set of life-cycle operations for class `X` is:

```cpp
class X {
    X (someargs);  Ordinary constructor, to create on object of type X

    X();    Default constructor
    X(const X&);  Copy constructor
    X(X&&);  Move constructor
    X& operator = (const X); Copy assignment
    X& operator = (X&&); Move assignment
    ~X();    Destructor, to clean up
};
```

The descriptive text inside the declarations is slide annotation, not valid C++ comments. The intended operations are ordinary constructors, default constructor, copy constructor, move constructor, copy assignment, move assignment, and destructor.

### Constructors and Destructors

Constructors and destructors are paired actions. Object lifetime starts with construction and ends with destruction.

#### Tracer Example

```cpp
#include <iostream>
struct Tracer {
    std::string mess;

    Tracer(const string& s) : mess{s}
    {
        std::cout << mess;
    }

    ~Tracer()
    {
        std::cout << "~ " << mess;
    }
};
```

`Tracer` stores a message, prints it when constructed, and prints a marked version when destroyed. The source omits `std::` before `string` in the constructor parameter; the intent is clear if `string` is in scope.

```cpp
int main()
{
    Tracer object{"a string"};
}

The output to the terminal is...
```

This source block mixes C++ and slide text. The object is constructed inside `main` and destroyed when it goes out of scope.

```cpp
int main()
{
    Tracer tr{"a string"};
}
```

The output is:

```text
a string
~ a string
```

First the constructor prints `a string`. Then `tr` goes out of scope, so the destructor prints `~ a string`.

#### Constructors and Invariants

A constructor has the same name as the class and no return type. It establishes **invariants**, which are rules that should hold throughout the object lifetime.

When invariants are specified up front, they clarify class behavior, simplify member functions, document resource management, and reduce edge cases. If a constructor cannot enforce the invariants, for example because its arguments are invalid, it must not create the object.

If construction is halted, acquired resources must be released. This avoids resource leaks during failed construction.

#### Destructor and RAII

A destructor is written with `~` followed by the class name, such as `~X`. A class has only one destructor, and it takes no arguments.

The destructor is guaranteed to run when an object is destroyed. This supports **Resource Acquisition Is Initialization (RAII)**:

- the constructor acquires resources, such as memory or files;
- the destructor releases them;
- users of the class do not manage the resource manually.

Destructors are usually called implicitly:

```cpp
void f()
{
  Tracer tr{"a string"};
  tr goes out of scope: ~Tracer() is called on tr
}
```

The line about going out of scope is slide text, not C++. The key point is that automatic objects are destroyed at the end of their scope.

```cpp
Tracer* tr = new Tracer{"a string"};
// some code
delete tr;
tr is deleted: ~Tracer() is called on tr
// more code
```

Again, the explanatory line is slide text. For a free-store object created with `new`, `delete` invokes the destructor and releases the storage.

#### Construction and Destruction Order

Constructor execution has a fixed order:

1. If the class derives from a base class, the base constructor is called.
2. Data members are constructed.
3. The constructor body executes.

Destructor execution happens in reverse:

1. The destructor body executes.
2. Data members are destroyed.
3. The base class destructor is called.

This order matters because constructor bodies run after members already exist, and destructor bodies run before members are destroyed.

### Initialization

#### Initialization Without Constructors

Built-in types such as `int` and `char` do not have user-defined constructors. They can only be initialized with values, for example `int a{1};`.

For simple aggregate types, objects can be initialized without defining a constructor.

```cpp
struct Work {
    std::string name;
    int number;
};
```

```cpp
Work some_work {"Teach", 19};
std::cout << some_work.name << " " << some_work.number;
```

The source had mismatched code fences around this example. The idea is **member-wise initialization**: public members are initialized in declaration order.

Copy initialization also works member-wise:

```cpp
Work other_work {some_work};
std::cout << other_work.name << " " << other_work.number;
```

Default initialization with braces initializes every member with `{}`:

```cpp
Work df_work {};
std::cout << df_work.name << " " << df_work.number;
// empty string "" and 0
```

Do not forget the braces. Without `{}`, behavior differs by storage duration and member type. Static objects are zero/default initialized. Local and free-store objects with built-in members may leave those members uninitialized, while user-defined members such as `std::string` are default-initialized.

```cpp
void f()
{
    Work df_work {};
    std::cout << df_work.name << " " << df_work.number;
    // empty string "" and 0

    Work df_without_curly_braces;
    std::cout << df_without_curly_braces.number;
    // undefined value!
}
```

`df_work.number` is `0`. `df_without_curly_braces.number` has an undefined value because `number` is a built-in local member that was not value-initialized.

#### Initialization With Constructors

If an ordinary constructor is defined:

1. the default constructor disappears;
2. the user-provided ordinary constructor must be used;
3. the copy constructor still exists.

```cpp
struct Work {
    std::string name;
    int number;
    Work(std::string a) : name{a} {number = name.length();}
};
```

```cpp
Work some_work {}; // error
Work other_work {"long_thread"};
std::cout << other_work.name << " " << other_work.number;
```

`some_work {}` is invalid because no default constructor is available. `other_work` calls the constructor and sets `number` from the string length.

#### Universal and Uniform Initialization

The source describes `{}` as universal and uniform initialization:

```text
{}: universal and uniform initialization

- a constructor can be called with ( ) or {} or = (in some cases)

- it is usually a good practice to use {} to highlight initialization is happening

- {} is defined as universal and uniform initialization
  X* p = new X{4}; // ok!
  X* p2 = new X=4; // wrong!

- The main reason to use ( ) instead of {} is to make sure a constructor is called for initialization
  - {} may mean a member-wise or initializer-list initialization

std::vector<int> v1 {77}; // 1 element with value 77
std::vector<int> v2 (77); // 77 elements with value 0
```

The key distinction is that braces can select initializer-list or aggregate initialization, while parentheses call a constructor directly. For `std::vector<int>`, `{77}` creates one element with value `77`; `(77)` creates 77 default-initialized elements.

#### Default Constructors

A **default constructor** can be invoked without arguments. A constructor with default arguments can become a default constructor, but this should be used carefully.

```cpp
struct Work {
    Work(std::string a ="work") : name{a} {};
};
```

The source used curly quotes around `"work"`; the valid C++ form uses normal quotes.

Default constructors are needed when a default value makes sense or when the type is used as an element type in a data structure such as an array or vector.

Built-in types have default constructors, but they are not implicitly invoked for local or free-store variables without braces:

```cpp
void f() {
  int a {}; // 0
  int a1; // undefined value
}
```

If a class has reference or const data members, those members must be initialized when the object is constructed. Use in-class initializers or define a default constructor that initializes them.

```cpp
struct Work {
  char& flag_ref;
  const char flag{'a'}; // in-class initializer
  Work() {flag_ref[flag]; }; // default constr
```

This source snippet is incomplete and likely malformed. The main point is that references and const members require explicit initialization.

#### Initializer-List Constructors

An **initializer-list constructor** has an argument of type `std::initializer_list<T>`. It accepts an arbitrary number of homogeneous arguments.

`std::initializer_list<T>` is passed by value efficiently because it is a small handle-like type. It has iterators, but its values are immutable, so no move operations are performed from the list elements.

Overload resolution has special rules:

- if ambiguity is between a default constructor and an initializer-list constructor, the default constructor is used for `{}`;
- if ambiguity is between an initializer-list constructor and an ordinary constructor, the initializer-list constructor is used.

```cpp
struct X {
    X(initializer_list<int>);
    X();
    X(int);
};

X x0 {}; // empty list: default constructor
X x1 {1}; // one integer: initializer-list constructor
X x2 (1); // explicitly call X(int);
```

`x0` uses the default constructor, `x1` uses the initializer-list constructor, and `x2` uses the ordinary `int` constructor because parentheses are explicit.

```cpp
template<class T> class Vector {
public:
    Vector(std::initializer_list<T> s);
// ...
private:
    int sz;
    T* elem;
    void reserve(int size);
};

template<class T>
Vector::Vector(std::initializer_list<T> s) : sz{s.size()}
{
    reserve(sz); // get the right amount of space
    std::uninitialized_copy(
        s.begin(), s.end(), elem);
    // initialize elements in elem[0:s.size()]
}
```

This `Vector` constructor allocates enough space for the list and initializes the elements by copying from the initializer list.

#### Member Initialization

When an object is constructed, all its members must be initialized. A constructor can use a **member initializer list**.

```cpp
ClassName::ClassName(T1 arg1, T2 arg2) :
    member1{arg1},
    member2{arg2}
{
    // body
    the constructors of the members
    - are called before the body is executed
    - are called in the order of declaration in the class definition (better to use the same order in the member initializer list)
    - if a member does not need arguments for initialization, it can be omitted - but it is better to comment why
}
```

The bullet text inside the body is slide annotation. The important rule is that members are initialized before the constructor body, in declaration order, not in the textual order of the initializer list.

Member initializers are also more efficient:

```cpp
Person::Person(std::string& n, std::string& a) :
name{n}
{
    address = a;
}
```

Here `address` is first default-initialized before the constructor body, then assigned `a`. Initializing `address{a}` in the member initializer list would avoid the extra default initialization plus assignment.

#### Delegating Constructors

If multiple constructors repeat the same action, options include duplicating code, calling a shared helper function, or defining one constructor in terms of another.

```cpp
ClassName::ClassName(T1 arg1) : ClassName{f(arg1)} {}
```

This is a **delegating constructor**. `f` may convert or validate the argument. A delegating constructor cannot also explicitly initialize other members in the same initializer list. Calling another constructor inside the body would create a temporary object and would not initialize the current one.

One approach is to use a shared function:

```cpp
class X {
    int a;
    validate(int x) {
        if (0 < x && x <= max) {a=x;}
        else throw Bad_X(x);
    }
public:
    X(int x) { validate(x); }
    X() { validate(22); }
    X(string s) { int x = to<int>(s); validate(x); }
// ...
};
```

The source tagged this as Java, but it is C++. The helper `validate` centralizes invariant checking.

Another approach is constructor delegation:

```cpp
class X {
    int a;
public:
    X(int x) {
        if (0 < x && x <= max) {a=x;}
        else throw Bad_X(x);
    }
    X() : X{22} {}
    X(string s) : X{to<int>s} {}
// ...
};
```

The expression `to<int>s` is likely corrupted and should probably be a conversion call such as `to<int>(s)`. The intent is that the `string` constructor converts the string and delegates to `X(int)`.

### Copy

#### Copy Operations

`x = y` is a proper copy if it satisfies two properties:

- **equivalence**: after copying, operations on `x` and `y` produce the same results;
- **independence**: after copying, operations on `x` do not change the state of `y`.

C++ provides:

- **copy constructor**: `X(const X&)`, which initializes a new object from an existing object;
- **copy assignment**: `X& operator=(const X&)`, which assigns into an already constructed object and must handle its existing resources.

The compiler can generate default copy operations that perform member-wise copy. This is correct for many simple types but can be wrong when members are owning pointers.

```cpp
struct Work {
  std::string name;
  int number;
  ...
  Work(const Work & w) : name{w.name}, number{w.number} {}
};
```

This custom copy constructor copies the values of `name` and `number`.

#### Shallow Copies and Shared State

If a class has pointer members, default copy copies the pointer values, not the pointed-to objects. This creates **shallow copy** and shared state. It violates independence because modifying one object can change the state observed through the other.

```cpp
struct S {
    int* p;
};

void f()
{
    // create a new object
    S x {new int{0}};
    // copy with default copy
    S y {x};
    // any change on y also changes x
    *(y.p) = 1;
    std::cout << *(x.p);
}
```

Both `x.p` and `y.p` point to the same `int`. After `*(y.p) = 1`, reading `*(x.p)` prints `1`. The source diagrams describe both objects storing the same address:

```text
x state: 0x1223414f2
shared: 0
y state: 0x1223414f2
```

and after modification:

```text
x state: 0x1223414f2
shared: 1
y state: 0x1223414f2
```

To avoid shallow copy, provide a user-defined copy constructor and assignment that perform **deep copy**.

```cpp
struct S {
    int* p;
    S (const S& a) : p{new int{*a}} {}
};

void f2()
{
    // create a new object
    S x {new int{0}};
    // copy with non-default deep copy
    S y {x};
    *(y.p) = 1;
    std::cout << *(x.p);
}
```

The source likely contains a bug: `*a` is invalid because `a` is an `S`, not a pointer. The likely intended form is `new int{*a.p}`. The concept is to allocate a new `int` and copy the pointed value.

### Move

#### Move Operations

After `x` is moved to `y`, `y` owns the resources or values that `x` had. `x` remains valid and destructible, but it no longer owns those resources and may not have its previous logical value.

C++ provides:

- **move constructor**: `X(X&&)`, which initializes a new object by taking resources from an rvalue argument;
- **move assignment**: `X& operator=(X&&)`, which transfers resources into an already existing object.

Move arguments are non-const rvalue references because the source object may need to be modified.

Move operations are useful for resource handles because moving avoids acquiring new resources. For built-in types, moving is effectively copying. The compiler can use move operations when returning from a function or when an argument is an rvalue reference.

`std::move` does not move anything by itself. It casts its argument to an rvalue reference so that the move constructor or move assignment can be selected if available; otherwise a copy may be used.

#### Move-Based Swap

The old-style swap uses copies:

```cpp
template<class T>
swap(T& a, T& b) // "old-style swap"
{
    T tmp {a}; // two copies of a
    a = b; // two copies of b
    b = tmp; // two copies of tmp (aka a)
}

3 copy operations + destructors + memory consumption
```

The last line is slide text. The point is that copy-based swap may allocate, copy, and destroy unnecessary temporary state.

A move-based version casts objects to rvalue references:

```cpp
template<class T>
swap(T& a, T& b)
{
    T tmp {static_cast<T&&>(a)};
    a = static_cast<T&&>(b);
    b = static_cast<T&&>(tmp);
}
```

This is equivalent in intent to using `std::move`.

```cpp
std::move() does not move, but casts to an rvalue reference so that types with move constructors or assignment can exploit it

T tmp {std::move(a)};
a = std::move(b);
b = std::move(tmp);
```

The first line is explanatory text inside the code block, not valid C++. The valid code uses `std::move` to enable move construction and move assignment, avoiding unnecessary copies when `T` supports move operations.

### Default Operations

By default, a class may have:

- default constructor;
- default copy constructor;
- default move constructor;
- default copy assignment;
- default move assignment;
- default destructor.

The compiler generates these operations if they are used and eligible. Generated operations apply member-wise to non-static data members and base subobjects.

A developer can control default generation:

- if a constructor is declared, the default constructor is not generated;
- if one copy, move, or destructor operation is declared, related copy/move/destructor operations may not be default-generated.

The `= default` syntax explicitly requests compiler-generated behavior.

Relying on compiler-generated operations is often safer than writing custom code, but only when member-wise behavior is correct. Watch for shallow copies, member initialization behavior, and built-in members that remain uninitialized in local or free-store objects.

#### Defaults and Resource Handles

The source gives a handle class that owns an object created with `new`:

```cpp
template<class T>
class Handle {
    T* p;
public:
    Handle(T* pp) :p{pp} { }
    T& operator*() { return *p; }
    ~Handle() { delete p; }
};
```

This destructor deletes `p`, so `Handle` owns the pointed object. However, default operations are dangerous for owning pointers:

- the default constructor does not initialize the pointer;
- the default destructor alone would not know ownership unless written explicitly;
- default copy and move are wrong if the pointer represents ownership, because they create shared state or double-delete risks.

This is why resource handles need carefully designed copy/move/destructor behavior.

### Deleted Functions

The `= delete` syntax prevents the compiler from using an otherwise available function or conversion.

```cpp
class X {
    X(int);
    X(double) =delete;
}
X(1); // ok
X(0.1); // does not compile

- control where a class can be allocated
    - =delete the new operator -> the class cannot go on the free store
    - =delete the destructor -> the class cannot go on the stack
    - deleting the destructor is not a good practice, because then objects cannot be actually destroyed - better to make it private
```

The block mixes C++ and slide text, and the class declaration is missing a semicolon. The key idea is that `X(double) = delete;` rejects construction from `double` even if conversion might otherwise be possible. Deleted functions can also restrict allocation patterns, although deleting destructors is usually poor practice; making a destructor private is often clearer.

## Final Summary

C++ object lifetime is controlled by construction, destruction, copy, and move operations. Constructors establish invariants, destructors release resources, and RAII makes resource management automatic and exception-safe. Initialization rules matter: braces usually make intent clearer, but initializer-list constructors and aggregate initialization can affect overload selection.

Copy operations must preserve equivalence and independence. Default member-wise copy is fine for simple values but dangerous for owning pointers, where shallow copies create shared state or double deletion. Move operations transfer resources efficiently while leaving the source object valid. Compiler-generated defaults are useful when they match class semantics, and `= delete` is a precise way to forbid unwanted operations.
