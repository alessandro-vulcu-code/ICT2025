## Study Notes

This lesson follows **[c++pl] Chapters 9 and 11** and Chapter 3 of Scott Meyers, *Effective C++: 55 Specific Ways to Improve Your Programs and Designs*. It explains memory areas, `new` and `delete`, common resource errors, and RAII.

### C++ Program Memory

Different areas of memory have different uses and lifetimes.

#### Const Data and Stack

The **const data area** stores data known at compile time. According to the source, it contains built-in data, is available throughout the whole program lifetime, and is read-only.

The **stack** stores automatic variables, such as local variables in functions. Stack memory is allocated sequentially just before an object is created and deallocated sequentially during stack unwinding. Programmers do not directly manipulate stack allocation.

#### Free Store and Static Memory

The **free store**, also called the **heap**, is memory allocated with `new` and released with `delete`. Allocation lifetime may not match object lifetime cleanly if the programmer manages it incorrectly. This storage can be accessed through `void*`, but raw memory access gives no direct object-level access to non-static members or functions until an object is properly constructed.

**Global/static memory** stores global and static variables. The source states that it is initialized the first time a global or static variable is met during program execution.

### new and delete

The free store is accessed through `new` and `delete`.

#### Single Objects

`new` initializes memory, constructs an object, and returns a pointer to that object. `delete` calls the destructor when needed and deallocates the heap memory.

Use `{}` or `()` when initializing with `new`.

```cpp
void f() {
  int* a {new int{10}};
  // some code
  delete a;
}
```

This allocates an `int` on the free store, initializes it to `10`, and later releases it. The programmer must ensure that every successful `new` is matched by exactly one correct `delete`, unless ownership is transferred to a resource-managing object.

#### Arrays

Arrays can be allocated with `new[]` and released with `delete[]`. `delete[]` deallocates the whole array; ordinary `delete` applies to a single object and must not be used for arrays.

C++ implementations need enough information to delete the object or array correctly. Allocations performed with `new` may therefore carry a small overhead to store size or bookkeeping information.

#### operator new and operator delete

The source lists low-level allocation functions:

```cpp
// allocate space for individual object
void* operator new(size_t) throw(std::bad_alloc);

// if (p) deallocate space allocated using operator new()
void operator delete(void* p);

// allocate space for array
void* operator new[](size_t) throw(std::bad_alloc);

// if (p) deallocate space allocated using operator new[]()
void operator delete[](void* p);

new operator vs operator new():
  - the second (operator new()) can be used by the first to allocate size_t uninitialized memory
  - the first (new) is used to construct an object on the free storage or heap, i.e., in order, it calls operator new() and then the constructor of the object
```

This block mixes C++ declarations and slide text. The distinction is important: the **new expression** constructs an object, while **`operator new()`** only allocates raw uninitialized storage. Similarly, `delete` destroys an object and releases storage, while `operator delete()` performs the deallocation step.

These functions are declared in `<new>`, although ordinary use of the `new` expression does not require explicitly including that header.

#### Placement new

`operator new` can be overloaded with extra parameters. A common example is **placement new**, where an object is constructed in memory that has already been allocated.

```cpp
char *buf = new char[sizeof(string)]; // pre-allocated buffer
std::string *p = new (buf) std::string("hi"); // placement new
std::string *q = new std::string("hi"); // ordinary allocation
```

`p` points to a `std::string` constructed inside `buf`. `q` points to a `std::string` allocated and constructed normally. Placement new is low-level and requires careful manual destruction and storage management.

### Memory Management Issues

Managing free-store memory manually is difficult because the programmer must track object state, ownership, and lifetime.

#### Memory Leaks

A **memory leak** occurs when code calls `new` but never calls `delete`. If this happens frequently, the system may run out of memory.

```cpp
int f() {
    int* a {new int{10}};

    if (*a = 10)
    {
        return 4;
    }
    delete a;
    return 5;
}
```

The condition uses assignment, `*a = 10`, not comparison. As written, it assigns `10` and evaluates as true, so the function returns before `delete a;` is reached. The memory pointed to by `a` is leaked. The likely intended comparison would be `*a == 10`, but even then the early return would still skip deletion unless handled carefully.

#### Premature Deletion

A **dangling pointer** occurs when code deletes an object and later reuses the pointer. The pointer still stores an address, but the object no longer exists there.

```cpp
int f() {
    int* a {new int{10}};

    if (*a = 10)
    {
        delete a;
    }

    // some code
    *a = 5;
}
```

Again, `*a = 10` is assignment. If deletion occurs, `a` becomes dangling. Writing `*a = 5;` may write into memory now used for something else, causing undefined behavior.

#### Double Deletion

**Double deletion** happens when code calls `delete` twice on the same allocation. This can corrupt memory.

```cpp
int f() {
    int* a {new int{10}};

    if (*a = 10)
    {
        delete a;
    }

    // some code
    delete a;
}
```

If the first `delete` runs, the second `delete` attempts to release already released memory. This is undefined behavior and may corrupt the allocator's internal state.

### Resource Management

The same problems apply to resources in general. A **resource** is something obtained from the operating system and later returned to it. Examples include heap memory, files, locks for concurrency, and sockets.

The lesson focuses on memory, but the same management principles apply to other resources.

### Efficient Memory Management

Do not use `new` for local objects when stack allocation is enough. Local objects can be created directly on the stack, which gives automatic cleanup.

Do not use naked `new` and `delete`. Use **handle classes** that own resources and release them automatically.

#### RAII

**Resource Acquisition Is Initialization (RAII)** means acquiring a resource and immediately giving control of it to a resource-managing object. The same statement initializes the handle and acquires the resource.

The handle object's destructor releases the resource. Since destructors are automatically called when objects go out of scope, RAII prevents many leaks and cleanup bugs.

#### Simple Handle Class

```cpp
class Handle {
    int* p; // pointer to int
public:
    Handle(int* pp) :p{pp} { }
    int& operator*() { return *p; }
    ~Handle() { delete p; }
};

// example of usage
void f()
{
    Handle obj_handle {new int{10}};
    std::cout << *obj_handle;
} // obj_handle goes out of scope
// and calls delete on p
```

`Handle` owns an `int*`. Its destructor calls `delete p`, so the resource is released when `obj_handle` goes out of scope. It overloads `operator*`, so dereferencing the handle returns the referenced `int`.

This example still needs careful copy semantics: if the compiler-generated copy constructor copies `p`, two handles would own the same pointer and may both delete it.

#### Copy Semantics for Handles

Default copying can be wrong for handle classes because of shallow copy. The source lists four strategies:

1. **Prohibit copying**, using `= delete` or a private copy constructor, when copying the resource does not make sense.
2. **Reference-count the resource**, increasing a count when another handle points to the same resource.
3. **Transfer ownership**, which is close to move semantics.
4. **Copy the underlying resource**, performing a deep copy.

The correct strategy depends on what ownership means for the resource.

#### Access to Raw Resources

Sometimes a handle must expose the underlying resource, for example when an API expects the raw resource as an argument. This may weaken encapsulation, but it is often practical.

Two common approaches are:

- explicit getter methods;
- implicit access through overloaded operators, such as `operator*`.

The interface should make ownership clear: exposing access to a resource should not accidentally transfer ownership unless the function explicitly says so.

## Final Summary

C++ memory is divided into regions with different lifetime rules: const data, stack, free store, and static/global storage. `new` and `delete` manually manage free-store objects, but manual management is error-prone. Common failures include leaks, dangling pointers, and double deletion.

The preferred C++ strategy is **RAII**: acquire a resource inside a handle object and release it in the destructor. This makes cleanup automatic at scope exit. Handle classes must still define correct copy and move behavior, because default shallow copying is usually wrong for owning pointers.
