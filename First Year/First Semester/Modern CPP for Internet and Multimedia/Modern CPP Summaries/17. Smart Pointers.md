# Briefing on Smart Pointers in Modern C++

## Executive Summary

This document synthesizes key concepts regarding the use of smart pointers in Modern C++ as a solution to the prevalent issues of resource management associated with raw pointers. The primary problems with manual memory management using `new` and `delete` are memory leaks and dangling pointers, which lead to resource exhaustion and undefined behavior, respectively. These issues arise when cleanup code (`delete`) is missed due to exceptions, early returns, or complex code paths.

The core solution presented is the **Resource Allocation Is Initialization (RAII)** paradigm, implemented in the C++ Standard Library through three types of smart pointers:

1. `**std::unique_ptr**`: A lightweight, scoped pointer that enforces exclusive ownership. It cannot be copied, only moved, ensuring that only one pointer owns the managed resource at any time. The resource is automatically deallocated when the `unique_ptr` goes out of scope.
2. `**std::shared_ptr**`: A smart pointer that enables shared ownership of a resource. It maintains a reference count of how many `shared_ptr` instances point to the same object. The resource is deallocated only when the last `shared_ptr` is destroyed, and the reference count drops to zero.
3. `**std::weak_ptr**`: A non-owning smart pointer that observes an object managed by a `shared_ptr` without affecting its reference count. Its primary purpose is to break circular references between `shared_ptr` instances, which would otherwise cause memory leaks.

The document concludes by outlining best practices, such as assigning a newly allocated object to a smart pointer immediately upon creation (preferably using `std::make_shared`), to prevent common pitfalls.

## The Problem with Raw Pointers

Manual memory management using raw pointers is a significant source of bugs in C++. The fundamental rule is that every call to `new` must be matched by a corresponding call to `delete`. The central challenge is determining who is responsible for this `delete` operation, which often leads to two major types of errors: memory leaks and dangling pointers.

### Memory Leaks

A memory leak occurs when memory allocated on the heap (or free store) is no longer referenced by any part of the program but has not been deallocated. This typically happens when the `delete` statement is skipped due to an alternative execution path.

**Example of a Potential Leak:** A function that allocates a buffer may fail to deallocate it if an early `return` or an exception occurs before the `delete[]` statement is reached.

```cpp
int performTask() {
  char* buffer = new char [256];
  ...
  ...// Some code here
  ...// that may trow exception
  ...// or return something
  ...// before the end is reached
  ...
  delete []buffer;
  return 0;
}
// THIS IS A LEAK!
```

**Example of a Definite Leak:** In this scenario, if `<some_condition>` is true, the function returns without deallocating `buffer`.

```cpp
int performTask() {
  char* buffer = new char [256];
  ...
  if(<some_condition>) {
    return 1; // LEAK: delete[] is skipped
  }
  delete []buffer;
  return 0;
}
```

Manually managing every possible exit path with a `delete[]` call is error-prone, difficult to maintain, and leads to messy code.

### Dangling Pointers

A dangling pointer is a pointer that continues to reference a memory location after the object at that location has been deallocated. Accessing a dangling pointer results in undefined behavior, one of the most dangerous types of bugs in C++.

**Example of a Dangling Pointer:**

```cpp
char* buffer = new char [256];
delete []buffer;
std::cout << *buffer; // Accessing a dangling pointer! Undefined Behavior.
```

The behavior is particularly insidious because the memory might not be immediately overwritten, meaning tests could pass while the bug remains latent. A dangling pointer can be neutralized by setting it to `nullptr` after deletion.

```cpp
char* buffer = new char [256];
delete []buffer; // buffer is now dangling
buffer = nullptr; // buffer is no longer dangling
```

## The RAII Solution: Smart Pointers

The recommended solution to these problems is to use the **RAII (Resource Allocation Is Initialization)** principle. This is achieved by using wrapper classes that allocate a resource in their constructor and deallocate it in their destructor. The C++ Standard Library provides three primary smart pointer classes for this purpose.

- `std::unique_ptr`: For exclusive, scoped ownership.
- `std::shared_ptr`: For shared ownership between multiple methods or threads.
- `std::weak_ptr`: To prevent circular references when using `shared_ptr`.

These smart pointers can be used with the `->` operator just like raw pointers.

## `std::unique_ptr`: Exclusive Ownership

A `unique_ptr` is a scoped pointer that models exclusive ownership. It is the most lightweight smart pointer.

### Core Characteristics

- **Construction:** Its constructor takes a raw pointer created with `new`.
- **Destruction:** Its destructor automatically calls `delete` on the wrapped pointer when the `unique_ptr` goes out of scope or is reassigned.
- **Ownership Model:** It cannot be copied, only moved. This compile-time check prevents multiple pointers from owning and attempting to delete the same resource.



### Ownership Transfer and Function Arguments

Because `unique_ptr` cannot be copied, passing it to a function requires a deliberate transfer of ownership.

- **Passing by Value (Move):** Transferring ownership to a function is an explicit move operation. If the function takes the `unique_ptr` by value, the caller must use `std::move`. The object will be destroyed when the function scope ends.
- **Solution 1: Move and Return:** A function can take ownership via `std::move` and then return the `unique_ptr` by value, which implicitly moves it back to the caller.
- **Solution 2: Pass by Reference:** If a function only needs to observe or use the object without taking ownership, it should be passed by reference (typically `const` reference).

```c++
void function f1(std::unique_ptr<T1> up) { //do stuff }

std::unique_ptr<T1> up1 (new T1 ());

f1(up1); // not allowed!!

f1(std::move(up1)); // IT WORKS, BUT BE AWARE THE OBJECT IS DESTROYED INSIDE THE FUNCTION f1 !!!
```

```c++
//wrong uses of unique pointers
int main{
	int a; // a is in the stack
	std::unique_ptr<int> up(&a); // a will go out of scope, double deletion
	
	int *p = new int{10};
	{
	std::unique_ptr<int> up(p);
	}
	//up is destroyed and the delete is already called, so we have a dangling pointer
	delete p; 
}

```
### Utility Methods

- `release()`: Returns the raw pointer and releases ownership. The caller becomes responsible for deleting the pointer. The `unique_ptr` is set to `nullptr`.
- `reset()`: Destroys the managed object.
- `reset(new_ptr)`: Destroys the old object and takes ownership of a new pointer.

## `std::shared_ptr`: Shared Ownership

A `shared_ptr` represents shared ownership of an object. It uses a reference count to track how many `shared_ptr` instances point to the same resource.

### Core Characteristics

- **Reference Counting:** When a `shared_ptr` is created or copied, a reference count is established or incremented.
- **Automatic Deallocation:** The destructor decrements the reference count. When the count reaches zero, the managed object is automatically deleted.

### Usage and Best Practices

- **Exception Safety with** `make_shared`**:** The preferred way to create a `shared_ptr` is with `std::make_shared`. This is exception-safe, as it prevents a potential leak if the object allocation succeeds but the `shared_ptr` control block allocation fails.

### Utility and Casting

- **Utility Methods:**
    - `use_count()`: Returns the current number of owners.
    - `reset()`: Decrements the count and releases ownership, becoming an empty pointer. (_Note: The source context uses_ `_use_reset()_`_, which is a typo; the standard is_ `_reset()_`).
    - `get()`: Returns the raw pointer.
- **Pointer Casting:** Special functions are provided for type casting `shared_ptr` instances.
    - `std::dynamic_pointer_cast<D>(s_ptr)`
    - `std::static_pointer_cast<D>(s_ptr)`
    - `std::const_pointer_cast<const D>(s_ptr)`
```c++
std::shared_ptr<B> pb = std::make_shared<D>(); 
std::shared_ptr<D> pd1 = std::dynamic_pointer_cast<D>(pb); 
if(pd1 != nullptr) {…} 
std::shared_ptr<D> pd2 = std::static_pointer_cast<D>(pb); 
std::shared_ptr<const D> c_pd =std::const_pointer_cast<const D>(pb);
```

## `std::weak_ptr`: Non-Owning Observation

A `weak_ptr` is used to break circular references that can occur when two objects managed by `shared_ptr` refer to each other.

### The Problem: Cyclic References

If two objects hold `shared_ptr`s to each other, their reference counts will never drop to zero, even when all external references are gone. This creates a memory leak.

**Example of a Cyclic Reference:**

```cpp
struct Son {
  shared_ptr<Mum> mum;
};
struct Mum {
  shared_ptr<Son> son;
};

main() {
  shared_ptr<Son> son1 = make_shared<Son>(); // Son obj use_count = 1
  shared_ptr<Mum> mum1 = make_shared<Mum>(); // Mum obj use_count = 1
  son1->mum = mum1; // Mum obj use_count = 2
  mum1->son = son1; // Son obj use_count = 2
}
// When main ends, son1 and mum1 are destroyed.
// Both objects still have a use_count of 1.
// CYCLIC REFERENCE → MEMORY LEAK!!
```

### The `weak_ptr` Solution

A `weak_ptr` holds a non-owning ("weak") reference to an object managed by a `shared_ptr`. It does not affect the reference count.

**Corrected Example:** By changing one or both of the "back-pointers" to `weak_ptr`, the cycle is broken.

```cpp
struct Son {
  weak_ptr<Mum> mum;
};
struct Mum {
  weak_ptr<Son> son;
};

main() {
  shared_ptr<Son> son1 = make_shared<Son>(); // Son obj use_count = 1
  shared_ptr<Mum> mum1 = make_shared<Mum>(); // Mum obj use_count = 1
  son1->mum = mum1; // Mum obj use_count is still 1
  mum1->son = son1; // Son obj use_count is still 1
}
// NOW THEY ARE CORRECTLY DESTROYED
```

### Characteristics and Usage

- Does not take ownership or affect the `use_count`.
- Cannot be dereferenced directly with `->` or `*`.
- `lock()`: To safely access the object, `lock()` must be called. It returns an empty `shared_ptr` if the object has been deleted (i.e., the `weak_ptr` is "expired"), or a valid `shared_ptr` if the object still exists.
- `use_count()`: Checks how many `shared_ptr` instances own the object.
- `expired()`: Returns `true` if `use_count()` is 0.

## Common Pitfalls and Best Practices

A critical error is creating multiple independent `shared_ptr`s from the same raw pointer. Each `shared_ptr` will have its own reference count, leading to multiple attempts to delete the same memory.

**Wrong Usage:**

```cpp
string* p = new string("ciao");
std::shared_ptr<string> sp(p);  // count = 1
std::shared_ptr<string> sp2(p); // ALSO count = 1. Now two control blocks exist.
// Both sp and sp2 will try to delete p. Undefined behavior.
```

**The Golden Rule:** An object should be assigned to a smart pointer as soon as it is created. The best way to enforce this is to use factory functions like `std::make_shared`.

```cpp
std::shared_ptr<string> sp1 = std::make_shared<string>("ciao");
```
