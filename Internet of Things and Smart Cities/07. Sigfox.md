# Long-range IoT Technologies: Introduction

## Long-Range Communication
"Long-range" generally refers to a cell diameter of **several kilometers**. This is typically enabled by cellular networks, which come with trade-offs:
* **High complexity** and **infrastructure cost**.
* Support for **very high data rates**.
* **Not designed for energy efficiency** (recharging mobile terminals is normal).

## Low-Power Wide Area Networks (LPWAN) 
LPWANs are a category of technologies designed to **jointly optimize** a combination of energy efficiency, data rate, communication range, and cost per device.

The following table compares LPWAN to other wireless network types:

| Parameter             | WSN (Wireless Sensor Network)  | WLAN (Wi-Fi)                   | Cellular networks            | LPWAN                             |
| :-------------------- | :----------------------------- | :----------------------------- | :--------------------------- | :-------------------------------- |
| **Range**             | Very short ($\sim1-3$ m)       | Short ($\sim10-100$ m)         | Long ($\sim1-5$ km)          | Very long ($\sim5-20$ km)         |
| **Energy efficiency** | Very high (tx. power $< 1$ mW) | Medium (tx. power $\sim80$ mW) | Low (tx. power $\sim500$ mW) | Very low (tx. power $\sim 20$ mW) |
| **Data rate**         | Low                            | Very high                      | High                         | Very low                          |
| **Cost**              | Low                            | Medium                         | Medium                       | Very low                          |

## LPWAN Features and Examples 
LPWAN technologies, which include **Sigfox**, **LoRa**, and **NB-IoT** (the latter being cellular-based), share key characteristics:
* **Long-range coverage** (up to 20 km, sometimes higher).
* **Very high energy efficiency**, allowing battery life up to 10 years.
* **Low communication/infrastructure cost**.
* **Low data rate** per device, but support for a **very large number of devices**.
* **Easy network implementation and deployment** (no need for detailed radio planning).
* **Mostly static** with limited support for handover and mobility due to a simple core network.

# Sigfox

## Overview
Sigfox is the first LPWAN technology, developed by the French company Sigfox. The core idea is to provide a Sigfox cloud platform through a subscription-based model.

The system architecture works as follows:
1.  **End Nodes** (devices) communicate via the **Sigfox Radio link** to **Sigfox Base Transceiver Stations (BTSs)**. This communication is managed by local operators.
2.  The BTSs forward the data to the **Sigfox Cloud** using a backhaul connection (e.g., 4G, xDSL, IP) for storage and processing.
3.  The **Sigfox Cloud** is composed of:
    * **Backend Servers:** Handle BTS management, monitoring, and message processing.
    * **Storage:** Stores modems metadata and messages.
    * **Frontend Servers:** Manage users/groups and modems.
4.  Data stored and processed in the Sigfox Cloud can be accessed in two primary ways:
    * **Web-Interface & Application Integration:** Users can access the data via a standard **Web browser** using HTTPS.
    * **Customer Application Server:** Customer servers can integrate with the Cloud using HTTPS, REST/JSON, or Email to receive data, API responses, alerts, and call backs.

# Sigfox Physical (PHY) Layer

## Simplicity and Ultra-Narrow Band (UNB)
The core keyword for the Sigfox PHY layer is **simplicity**: there is no connection, no configuration, and no signaling.
* Sigfox uses a proprietary **Ultra-Narrow Band (UNB)** wireless technology.
* Energy is highly concentrated into a very tiny portion of the bandwidth.
* This approach results in a **very limited data rate**.
* A key benefit is its **interference-immune** nature, as the UNB signal has a small bandwidth and is less impacted by conventional, wider-band interferers. 

## Modulation and Repetition
* **Modulation:** Sigfox uses Differential Binary Phase Shift Keying (**DBPSK**) and Gaussian Frequency-Shift Keying (**GFSK**).
* In **DBPSK**, bits are encoded as changes in the signal's phase. A data bit '0' means the phase is not reversed, while a data bit '1' means the phase is reversed. 
* **Repetition Scheme:** Each message is transmitted **3 times** (triplication). This provides more robustness by making it likely that at least one Sigfox station receives the signal. The Sigfox cloud/backend is responsible for handling and removing possible duplicate messages.

## Data Rate and Bandwidth
* In DBPSK, each symbol carries 1 bit of information (since '0' is no phase change and '1' is phase reversal).
* The symbol rate is generally less than or equal to the channel bandwidth.
* Therefore, in a typical **100 Hz-wide channel**, the maximum practical symbol rate is about 100 baud, which translates to **100 bit/s** for DBPSK (1 bit per symbol).

# Sigfox Frame Structure and MAC Layer

## Frame Structure 
The maximum frame size in Sigfox is **26 bytes**. The structure differs slightly between uplink (UL) and downlink (DL) frames:

### Uplink (UL) Frame
* **Payload:** Up to **12 Bytes**.
* UL transmission is more common than DL (e.g., for sensors to report data measurements).
* **Structure:** Preamble (4 bytes), Sync. (2 bytes), Device ID (4 bytes), Payload (variable $0\div12$ bytes), Auth. (variable, not specified in size), FCS (2 bytes).

### Downlink (DL) Frame
* **Payload:** Up to **8 Bytes**.
* **Structure:** Preamble (8 bytes), Sync. (13 bits), Flags (2 bits), FCS (1 byte), Auth. (2 bytes), Error codes (variable, not specified in size), Payload (variable $0\div8$ bytes).

## Transmission Times and Limits 
The system has very strict transmission limits, exemplified by the Sigfox Europe (RC1) configuration:

* **Duty Cycle (DC):** $1\%$. This means a device can transmit for a total of **36 seconds per hour**.
* **UL Data Rate:** 100 bit/s.
* **Hourly Limit (Raw Bits):** With the DC, a device can transmit 3600 bits/h, which equals **450 bytes/h**.
* **Limit for Unique Data:** Due to the repetition code (3 times), the limit for "new" data is $450/3 = 150$ bytes/h.
* **Frame Limit:** With a 26-byte frame size, a device can send approximately $450 / (26 \cdot 3) \simeq 6$ frames/h*.
* **Max UL Payload Limit:** This translates to a maximum useful payload of $12$ bytes $\cdot 6$ frames/h $= 72$ bytes/h, which is very limited.

This limited capacity is why Sigfox is only suitable for applications with limited data requirements, such as:
* GPS coordinates (lat x long): 6 bytes
* Temperature: 2 bytes
* State reporting: 1 byte

## MAC Layer
* **Transmission Initiation:** Transmission is always initiated by the end devices.
* **Protocol:** Sigfox uses **Unslotted ALOHA**, characterized by:
    * No channel sensing.
    * No synchronization.
    * No continuous connection.
* **Cycle:** End devices **periodically wake up** to transmit UL data, briefly listen for any downlink messages (like ACKs or commands), and then return to **sleep mode**.
* **Use Case:** This method is effective for regular data collection and monitoring but is **not ideal for command-and-control** applications, as any command must wait for a sensor-initiated transmission window.
