# Internet of Things and Smart Cities - Long Range (LoRa)

## Overview
This document covers LoRa technology, which stands for Long Range. LoRa was developed in France in 2009, and the LoRa Alliance was founded in 2015.

LoRa and LoRaWAN define different parts of the protocol stack:
* **LoRa:** The Physical (PHY) layer implementation.
* **LoRaWAN:** The rest of the protocol stack, specifically the MAC layer and higher layers (Application Layer).

The protocol stack layers are: Application Layer, MAC Layer, PHY Layer, and Radio Frequency Layer.

# LoRa Applications and Frequency Range

## Applications
LoRa is used for various large-scale IoT applications, including:
* **Smart agriculture:** Used for cattle management (e.g., tracking) and monitoring the health of soil. 
* **Smart cities:** Used for city networks, monitoring bus schedules, and other urban infrastructure.
* **Smart buildings:** Used for reading and collecting utility usage data.
* **Smart environment:** Used for fire monitoring systems.

# LoRa Physical (PHY) Layer

## Modulation 
* **Modulation Type:** LoRa utilizes **Chirp Spread Spectrum (CSS)** .
* **Mechanism:** Symbols are encoded by modulating a carrier that **changes frequency linearly in time** (chirps). This spreads the signal power across a wide region of the spectrum to resist frequency-selective noise.
* **Chirps:** The modulation uses both up-chirps and down-chirps, which are confined within the designated bandwidth.
* **Symbol Structure:** Each LoRa symbol corresponds to one complete chirp waveform, where the frequency increases linearly over the symbol duration, causing the amplitude peaks to get closer together.

## Spreading Factor
- Number of chips used to encode a symbol
- Each symbol is made of $2^{SF}$ and each symbol represents **SF bits** of information.
	- Example: SF = 2 → 2 bits to represent symbols → 22=4 possible symbols: {00,01,10,11}.
- The value 2 SF defines the number of discrete time steps (chips) to make up one chirp. Therefore, it is the resolution of the waveform.
- SFs influence data rate, time-on-air, battery life, and receiver sensitivity.
- In LoRa, SF can assume values between 7 and 12.

### Spreading Factor, Data Rate, and Time
The Spreading Factor ($\text{SF}$) is critical in determining transmission characteristics:
* **Symbol Duration ($\text{T}_S$):** The time to transmit a symbol is calculated as $\text{T}_{S} = \frac{2^{\text{SF}}}{B}$, where $B$ is the bandwidth.
* **Symbol Rate ($\text{R}_S$):** The number of symbols per second is $\text{R}_{S} = \frac{B}{2^{\text{SF}}}$.
* **Bit Rate ($\text{R}$):** The number of bits per second is calculated as $R = \text{SF} \cdot R_{S} = \frac{\text{SF} \cdot B}{2^{\text{SF}}}$.
* Increasing the $\text{SF}$ causes an exponential increase in symbol duration, which is the dominant factor, leading to a **decrease** in the overall bit rate. The energy consumption also increases as the symbol duration (Time on Air) increases.

### Spreading Factor Orthogonality
* **Pseudo-Orthogonal SFs:** LoRa $\text{SF}$ values are pseudo-orthogonal. This allows multiple signals using different data rates (i.e., different $\text{SF}$s) to be transmitted on the same channel and received simultaneously by the gateway without causing a collision.
* **Collision Resistance:** Signals using the same $\text{SF}$ can still be received without collision if their power difference is $\ge 6 \text{ dB}$.

### Code Rate (CR)
* **Forward Error Correction (FEC):** LoRa employs FEC using a Code Rate ($\text{CR}$), which adds a number of extra bits every 4 bits, with $\text{CR}$ ranging from 1 to 4.
* **Actual Bit Rate:** The final, actual bit rate is calculated by including the $\text{CR}$ correction in the formula:
$$R = \text{SF} \cdot \frac{B}{2^{\text{SF}}} \cdot \left(\frac{4}{4+\text{CR}}\right)$$
# LoRa Physical (PHY) Layer: Sensitivity and Adaptive Data Rate (ADR)

## Sensitivity
* **SF and Sensitivity:** Higher $\text{SF}$ values lead to a longer transmission duration (Time on Air, $\text{ToA}$). This allows the receiver to "accumulate" energy for a longer time.
	* **Better Sensitivity:** The result is **better sensitivity**—the receiver is capable of effectively receiving more corrupted signals. This translates to a longer communication range because the receiver can successfully receive over a more attenuated link.
	* **Minimum SNR:** The required minimum Signal-to-Noise Ratio ($\text{SNR}_m$) decreases as the $\text{SF}$ increases. For instance, $\text{SF}7$ requires $-7.5 \text{ dB}$, while $\text{SF}12$ requires $-20 \text{ dB}$. (transmitting for a longer amount of time, with higher consumption and lower SNR)

## Data Rate and Trade-offs 
The trade-off between $\text{SF}$ and performance parameters is key:
* **Higher $\text{SF}$** leads to a **Lower bit/data rate**, a **Higher $\text{ToA}$**, and a **Higher range**.
* The maximum allowed payload size at the application layer decreases as the $\text{SF}$ increases to help reduce the $\text{ToA}$.

## Adaptive Data Rate (ADR) 
* **ADR Mechanism:** The Adaptive Data Rate (ADR) is a mechanism used to select the optimal $\text{SF}$ based on the link conditions.
* **Objective:** The goal is to jointly optimize the communication quality, network capacity, and power consumption. The $\text{SF}$ should be large enough to ensure reach but not too large to waste energy.
* **Logic:**
    * If the link margin is high (good signal), the $\text{SF}$ can be **reduced** (data rate increased).
    * If the link budget is low (poor signal), the $\text{SF}$ should be **increased** (data rate reduced) to cope with the worse $\text{SNR}$.
* **Impact of ADR:** As $\text{SF}$ increases with distance from the gateway, the $\text{ToA}$ also increases, along with power consumption. The visualization shows that end devices far from the gateway (up to $14 \text{ km}$) use $\text{SF}12$ with the lowest bit rate, while those closest to the gateway use $\text{SF}7$ with the highest bit rate.

# LoRa Physical (PHY) Layer: Frame Structure

## Physical Frame Structure
The physical frame is composed of several fields, where the payload size can range from 0 to 255 bytes:

| Field | Length | Description |
| :--- | :--- | :--- |
| **Preamble** | $6-65535$ symbols | A well-known sequence of up-chirps and down-chirps. Longer preambles increase the likelihood of packet detection by the receiver. Typically 8 symbols. |
| **Mandatory Preamble** | $4.25$ symbols | Used specifically for synchronization (frame sync and frequency sync). |
| **Header** | $8$ symbols (explicit mode) | Contains the payload length, data rate configuration, and other settings. It is omitted in implicit mode (e.g., for fixed-length control messages). |
| **Payload** | $0-255$ bytes | The data being transmitted. |
| **CRC** | $0-2$ bytes | Cyclic Redundancy Check indication for the payload. |

## MAC Payload Structure
![[Pasted image 20251029090949.png]]
The **Payload** field in the physical frame is actually the encrypted MAC Payload, which has its own internal structure:

1.  **MHDR (MAC Header):** 1 byte. Specifies the message type (e.g., join-request, data up/down).
2.  **MAC Payload:** This section has a maximum size of $\le 255$ bytes and contains the core data and control information. It is composed of:
    * **FHDR (Frame Header):** $7-23$ bytes. Contains key addressing and control information:
        * **DevAddr:** (32 bits / 4 bytes) The device address.
        * **FCtrl (Frame Control):** 1 byte. Contains flags, such as whether to use the data rate specified by the gateway for uplink, whether the message acknowledges the reception of a previous message, or if the gateway has more data for the mote.
        * **FCntr (Frame Counter):** 2 bytes. A sequence number used for security and replay protection.
        * **Options:** $0...15$ bytes. Used for MAC commands to change data rate, power transmission, etc.
    * **FPort (Frame Port):** 1 byte. Defines the application port number. It only exists if application data is present.
    * **FRMPayload (Frame Payload):** $\le 242$ bytes. This is the application data itself.
3.  **MIC (Message Integrity Code):** 4 bytes. A digital signature used for security.

The minimum header of the MAC payload is 12 bytes (MHDR + FHDR + MIC), plus 1 byte for FPort if application data is sent.


# LoRa Time on Air (ToA) and Transmission Examples

## Time on Air (ToA) Calculation
The Time on Air ($\text{ToA}$) is the total time required to transmit a frame, calculated as the sum of the preamble time and the payload time: $\text{ToA} = t_{\text{preamble}} + t_{\text{payload}}$.

* **Preamble Time:** $t_{\text{preamble}} = (n_{\text{preamble}} + 4.25) \cdot T_s$, where $T_s$ is the symbol duration.
* **Payload Time:** $t_{\text{payload}} = (n_{\text{payload}}) \cdot T_s$, where $n_{\text{payload}}$ is the number of symbols in the payload.

The calculation of $n_{\text{payload}}$ is complex and depends on many parameters:
* Spreading Factor ($\text{SF}$).
* Payload bytes ($\text{PL}$).
* Header enabled status ($\text{H}$: implicit or explicit mode).
* Low Data Rate Optimization enabled status ($\text{DE}$).
* Code Rate ($\text{CR}$).

The full formula for $n_{\text{payload}}$ is derived from the Semtech SX1276 datasheet:
$$n_{\text{payload}} = 8 + \max\left(\left[\frac{8\text{PL} - 4\text{SF} + 28 + 16\text{CRC} - 20\text{H}}{4(\text{SF} - 2\text{DE})}\right] \cdot (\text{CR} + 4), 0\right)$$

The overall $\text{ToA}$ can be expressed in terms of $\text{SF}$ and $B$:
$$\text{ToA} = \frac{2^{\text{SF}}}{B} \cdot \left((n_{\text{preamble}} + 4.25) + n_{\text{payload}}\right)$$

## Transmission Time Examples
The Time on Air is highly dependent on both the Spreading Factor and the total packet size. For a fixed bandwidth ($B=125 \text{ KHz}$) and a packet size of 50 bytes:

| DR | SF | ToA ($\text{ms}$) |
| :--- | :--- | :--- |
| DR5 | 7 | $97.5 \text{ ms}$ |
| DR4 | 8 | $174.6 \text{ ms}$ |

# LoRa Transmission Times and Constraints

## Duty Cycle Limitations
LoRaWAN transmissions are subject to strict regulatory constraints, particularly the duty cycle:

* **Duty Cycle Rule:** In the European region (EU868), a common maximum duty cycle is **$1\%$**. This means the transmitter must be silent for $99\%$ of the time after a transmission. The total maximum transmission time is $36$ seconds per hour.
* **Impact of ToA on Message Count:** The Time on Air ($\text{ToA}$) dramatically limits the number of messages that can be sent per hour:
    * **High Data Rate Example ($\text{SF}7$):**
        * $\text{ToA}$ for a $100 \text{ B}$ packet is $189.7 \text{ ms}$.
        * The required silent time is $18.78 \text{ seconds}$.
        * Total cycle time is $\sim 18.97 \text{ s}$.
        * A device can send $\sim 190$ packets per hour (of $100 \text{ B}$).
    * **Low Data Rate Example ($\text{SF}12$):**
        * $\text{ToA}$ for a $100 \text{ B}$ packet is $4431.9 \text{ ms}$ (approx. $4.43 \text{ s}$).
        * The required silent time is $438.7 \text{ seconds}$ (approx. $7.3 \text{ minutes}$).
        * Total cycle time is $\sim 443.2 \text{ s}$.
        * A device can send only $\sim 8$ packets per hour (of $100 \text{ B}$).

## Fair Access Policy
In addition to the regulatory duty cycle, some network operators, such as The Things Network, implement a "Fair Access Policy" that further restricts usage:

* **Policy Limit:** This policy caps the average uplink Time on Air to **30 seconds per 24 hours per device**. This is a much stricter limit than the $1\%$ duty cycle ($\sim 36$ seconds per hour).
* **Consequence:** This policy effectively limits the number of messages a device can send per day to a very low number, particularly at high $\text{SF}$s.

A useful website: https://avbentem.github.io/airtime-calculator/ttn/eu868/100

The Fair Access Policy acts as a further constraint beyond the regulatory duty cycle:
* **Uplink Limit:** An average of **30 seconds of uplink Time on Air per 24 hours per device**.
* **Effective Duty Cycle:** This constraint is much stricter, equating to approximately $1.25 \text{ seconds/hour}$ (compared to $36 \text{ seconds/hour}$ for the $1\%$ duty cycle).
* **Downlink Limit:** At most **10 downlink messages per 24 hours**, which includes $\text{ACK}$s for confirmed uplinks.
* **Message Limits under FAP:** This policy drastically reduces the number of messages a device can send per day:
    * High Data Rate ($\text{SF}7$, $100 \text{ B}$ $\text{ToA} \approx 189.7 \text{ ms}$): $\sim 158$ packets per day.
    * Low Data Rate ($\text{SF}12$, $100 \text{ B}$ $\text{ToA} \approx 4.43 \text{ s}$): $\sim 6$ packets per day.

## LoRaWAN Architecture
LoRaWAN defines the components and recommended protocols for the network, which uses a **star-of-stars topology**.

The architecture involves four main components:
1.  **End Nodes:** End devices that perform sensing and actuating tasks. Each is identified by a $\text{DevEUI}$ (64 bits). 
2.  **Gateway (Concentrator):** Wireless base stations that receive messages from all End Nodes within range, based on the LoRa physical layer. They relay the messages to the Network Server using a backhaul link (e.g., $4\text{G}$, $\text{xDSL}$, Ethernet). Each is identified by a $\text{DevAddr}$ (32 bits).
3.  **Network Server:** The central element that:
    * Eliminates duplicate messages (since End Nodes transmit messages that can be received by multiple gateways).
    * Routes data.
    * Determines the optimal data rate (using $\text{ADR}$).
    * Selects the best Gateway to reach the End Node in Downlink ($\text{DL}$) transmissions based on link quality.
4.  **Application Server:** The final destination for application data.

**Security:** The system provides two layers of $\text{AES}$ security:
* **Network Session $\text{AES}$ secured messages** between the End Node and Network Server.
* **End-to-End $\text{AES}$ secured payload** between the End Node and Application Server.

# LoRaWAN End Node Classes and Channel Access

## Types of End Nodes (Classes A, B, and C)
LoRaWAN defines three distinct classes of End Nodes that dictate their bi-directional communication capabilities and, consequently, their energy consumption:

### 1. Class A (Base Class)
* **Communication:** Always initiated by the End Node (UL message is completely unsolicited and asynchronous).
* **Downlink (DL):** After sending an UL message, the End Node opens two short receive windows: $\text{RX}1$ and $\text{RX}2$. The $\text{DL}$ communication (e.g., commands or $\text{ACK}$) occurs during these windows. If the Network Server doesn't respond in $\text{RX}1$, it tries $\text{RX}2$. If neither responds, $\text{DL}$ must wait for the next $\text{UL}$ transmission.
* **Energy/Latency:** **Very low energy consumption** (most of the time in sleep mode) but **very large $\text{DL}$ latency**.
* **Use Case:** Periodic sensor measurements. 

### 2. Class B (Bi-directional Class)
* **Communication:** Operates as $\text{Class A}$ (with $\text{RX}1$ and $\text{RX}2$) but adds time-synchronized receive windows.
* **Downlink (DL):** The Gateway sends **beacons** every $128 \text{ seconds}$. The End Node uses these beacons for synchronization to open dedicated **ping slots ($\text{PS}$)**. These ping slots, which last $30 \text{ ms}$ each, allow the Gateway to initiate $\text{DL}$ transmissions.
* **Energy/Latency:** **Lower (bounded) $\text{DL}$ latency** ( $\text{DL}$ does not necessarily depend on $\text{UL}$ transmission) but **higher energy consumption** than $\text{Class A}$.
* **Use Case:** Utility meters (electrical, water), street lights. 

### 3. Class C (Continuous Receive Class)
* **Communication:** Operates as $\text{Class A}$, but the second receive window ($\text{RX}2$) remains **open continuously** until the next $\text{UL}$ transmission.
* **Downlink (DL):** $\text{DL}$ messages can be received at almost any time via $\text{RX}2$.
* **Energy/Latency:** **Very low $\text{DL}$ latency** but **very high energy consumption**.
* **Constraint:** $\text{Class C}$ devices are generally required to be connected to the mains (not battery powered).
* **Use Case:** Beacon lights, alarms.

## Channel Access Mechanism
* **Mechanism:** LoRaWAN relies on a random-access scheme known as **Pure ALOHA**.
* **Operation:** Each End Device transmits whenever it has data to send, with **no coordination** among nodes.
* **Collision Mitigation:** While collisions can occur, overlapping transmissions can still be decoded because the Spreading Factors ($\text{SF}$s) are quasi-orthogonal.
