### Classes and relationships
To develop complex concepts, it is necessary to express relationships among classes.
- **The "part of" relationship**
	- is expressed through data members;
	- example: the `car` class can have 4 private members of type `wheel`.
- **The "extends" relationship**
	- is expressed through class hierarchies.
	- this is the basis of OOP.

---

### Class hierarchies
- **Shape** is the **Base or super class**
- **Square** and **Circle** are **derived or sub classes**. They represent a more specific concept.

```c++
class Shape { ... }; [cite: 36]
class Square : public Shape { ... }; [cite: 36, 41]
class Circle : public Shape { ... }; [cite: 36, 35]
```

### Inheritance in C++
C++ supports hierarchies through two different mechanism:
1. **Implementation inheritance**
	1. Re-use the facilities provided by a base class
2. **Interference inheritance**
	1. use different derived class interchangeably (share same methods).
	2. Also known as run-time polymorphism.

---

### Derived classes
Is used to express the **extends** relationship, which is fundamental to OOP.
- Example: `Employee` and `Manager`
	- The `Employee` structure is used as the **base class** and contains general members like `first_name`, `family_name`, `hiring_date`, and `department`.
	- The `Manager` structure is a specific kind of employee, so it **re-uses** the base implementation of `Employee` and **extends** it by adding manager-specific characteristics.
	- The subclassing relationship is expressed as `struct Manager : public Employee { ... }`.
	- A `Manager` therefore has all the members of `Employee` plus its own members, such as `group` (list of employees) and `level`.

An object of a derived class can be used wherever an object of the base class is acceptable. This follows the **"is-a"** relationship (a `Manager` **is an** `Employee`):
- A `Manager*` is also an `Employee*`.
- A `Manager&` is also an `Employee&`.
- An `Employee` is **not** a `Manager*` (an explicit conversion would be needed).
- **Slicing Issue:** It's important **not** to pass a derived class object by value (e.g., passing a `Manager` object to an `Employee` parameter) to avoid **slicing**, where only the base class portion is copied.

---

### Member functions
Specific rules for accessing members of its base class:
- It can use the **public** and **protected** members of the base class
- It has **no access to private members**
- If a function is redefined in the derived class, the version from the base class can still be called using a **qualifier**.

---

### Constructors and Destructors
The execution order of constructors and destructors in class hierarchies is fixed:
#### Constructor Order
1. The constructor of the **base class** is called (if applicable).
2. The constructors of the **data members** of the derived class are called.
3. The **body** of the derived class constructor is executed.
- Each derived class can initialize the base class and its own members, **but not directly those of the base**.

#### Destructor Order
1. The **body** of the derived class destructor is executed.
2. The destructors of the **data members** of the derived class are called.
3. The destructor of the **base class** is called (if applicable).

- Destructors of base classes should generally be declared **virtual**.
- Declaring a base class destructor as `virtual` ensures the derived class's destructor is actually called, which is necessary since the derived class may have more resources or members that need proper clearing.

---

### Slicing with Copy Constructors
**Slicing** is a critical issue that occurs when using a pointer to the base class (e.g., `Employee*` referring to a `Manager*`) and calling a copy constructor that performs a member-wise copy.
- The issue is that only the copy of the **base members** is performed, and the derived class's members are left uninitialized.
- In the example `void f(X* p) { X h = *p; }`, if `p` points to a derived object `Y`, only the `X` part is copied to `h`.

**Solutions**
To prevent slicing, you can:
- Use `= delete` for the copy constructor in the base class.
- Make the base class inheritance private or protected (to be discussed later).

---

### Inheriting Constructors 
C++ allows inheriting all the constructors of a base class using `using X::X;`.
- **Note:** If the derived class has additional data members, they **would not be initialized** by the inherited constructors.
- To handle this, you can use **in-class initializers** for the additional members.

## Class Hierarchies

Class hierarchies can be complex, allowing for multiple levels and multiple inheritance1.

- **Structure:** It's possible to have **multiple base classes** (e.g., `Temp`, `Consultant` inheriting from other classes) or another **derived class as a base** (e.g., `Director` inherits from `Manager`).

### Navigating Class Hierarchies

When you have a base class pointer, such as `Base*`, it can point to an object of any derived type (e.g., an `Employee*` can point to an `Assistant*`, `Temp*`, `Manager*`, or `Director*`). This leads to ambiguity about the actual object's type.

There are four options to resolve this ambiguity:
1. Use objects of a single type.
2. Type fields.
3. Virtual functions.
4. Abstract classes.

---

#### 1. Single Type

You can ensure that a specific section of your program only contains pointers to objects of a single type (e.g., only `Assistants`). This is useful for homogeneous containers10. However, it relies on the developer to check this assumption, as it's **not enforced by the compiler**, which can lead to errors.

#### 2. Type Field

This technique involves adding a data member, like an `enum class`, to the base object to explicitly hold the type of the object.

- **Limitations:** The correctness is **not enforced by the compiler**. Furthermore, adding a new derived class requires changes to other existing classes, making this technique **limited and error-prone**.

#### 3. Virtual Functions

A function declared with the **`virtual`** keyword in the base class can be redefined, or "**overridden**," in a derived class.

- **Signature Rules:** The overriding function must generally keep the **same list of arguments** and the **same return type**. The exception is that return type pointers or references can be "relaxed" from the Base to the Derived class.
- **Guarantee:** The compiler and linker will ensure that the **correct function is called** based on the actual object type at runtime.
- A virtual function is defined in the base class and can be overridden in derived classes only if necessary.

---

#### Virtual in practice
Virtual functions enable **runtime polymorphism**. This means the correct implementation of a function is automatically selected based on the actual object type during execution.
- **Example:** In the `Employee` and `Manager` hierarchy, the base class `Employee` declares `print()` as `virtual`. `Manager` then **overrides** this method.
- When iterating through a `std::vector<Employee*>` , calling `elem->print()` will automatically select `Employee::print()` for an `Employee` object or `Manager::print()` for a `Manager` object.
- The objects must be manipulated with **pointers or references** to benefit from polymorphism. For direct manipulation, the type is known at compile time, leaving no space for polymorphism.
- If a derived class's overriding function needs to call the base class's implementation, it must use the qualifier, e.g., `Employee::print()`.

---

### Override Control
In complex class hierarchies, it can be difficult to control what is being overridden. A common issue is the **Hiding issue**, where declaring a function in a subclass with the same name but _different_ arguments hides the base function, even if it was virtual (meaning no override occurs).

C++ provides specific controls to manage inheritance: `virtual`, `override`, `final`, and `=0` (pure virtual/abstract classes).

1. `virtual`
	- Indicates that the function may be **overridden** in a derived class.
2. `override`
	- Used in derived classes (though optional).
	- Specifies that the function declaration **intends to override** a virtual function from a base class.
	- The compiler will **raise an error** if this override does not happen (e.g., if the function is accidentally hidden instead).
	- It is not part of the function's type and must be the **last word** in the declaration.
3. `final`
	- The `final` specifier is used to prohibit further overriding of functions or to prevent derivation from a class entirely.
	- A function can be declared `final` whether it is virtual or not.
	- When applied to a virtual function, `final` prohibits any derived class from further overriding that function. This is useful when it becomes clear after a few derivations that a function's specification shouldn't change, or that further specification is difficult or unnecessary.
	- `final` can also be used after a class name to prevent any further classes from deriving from it.
4. `Abstract classes`
	- **Abstract classes** are a mechanism for navigating class hierarchies and represent an interface for polymorphic types.
	- An abstract class is one that has at least one **pure virtual function**.
	- A pure virtual function is declared using the `=0` syntax: `virtual T pureVirtualFunction (U arg) = 0;`.
	- The definition of a pure virtual function is usually **not given** in the abstract class itself.
	- Objects of an abstract class type **cannot be created**.
	- Objects can only be created from derived classes that **override all** the pure virtual methods.
	- If a pure virtual function is not overridden, the derived class also remains abstract, which allows for the definition of implementation in stages.

---
### Access Control
- **`private`**: Accessible only by member functions and `friends` of the class where the member is declared.
- **`protected`**: Accessible by member functions and `friends` of the class where the member is declared **plus** those of the derived classes.
- **`public`**: Accessible by any function.

#### Use of `protected`
- `protected` is useful in class hierarchies but is **open to abuse**.
- **`protected` data members** are usually considered a design error.
	- They can lead to **data corruption** if improperly used in derived classes.
	- They make code restructuring hard because it's difficult to know which derived classes are using the member.
	- It's recommended to use the minimum number of data members in common base classes.
- **`protected` functions** are generally more useful.
	- **Virtual protected functions** can be overridden while being hidden from the object's public interface.

---

### Access Control for Base Classes
When deriving one class from another, the base class can be inherited with specific access levels, which affect the interface of the derived class.
- **Public Inheritance (`class X : public B`)**:
	- Creates a **subtype** (e.g., $X$ is a kind of $B$).
	- Allows for **runtime polymorphism**.
- **Private Inheritance (`class Y : private B`)**:
	- Restricts the interface and is used to inherit **implementation details**.
	- Only the derived class is aware it's inheriting from the base, so the base B **cannot be further derived** through the already derived class Y.
- **Protected Inheritance (`class Z : protected B`)**:
	- Similar to private inheritance, but the class Z **can be further derived**.
- **Default Access**: If not specified, the default inheritance access is **private for classes** and **public for structs**.

---

### Multiple Inheritance and Replication Issue
A class can inherit from **multiple base classes**. This is often used with public inheritance to inherit the interface and private/protected inheritance to inherit implementation details.
- **Replication Issue**: In the "diamond problem" scenario where class A inherits from B and C, and both B and C inherit from D, class A will contain **two separate objects of type D**.
	- If D is not an abstract class and has data, A may have **repeated members** (i.e., data from D is duplicated).
- **Solution: Virtual Base Classes**:
	- The replication issue can be solved by declaring the common base class **virtual** in the intermediate base classes.
	- Example: `class B : public virtual D` and `class C : public virtual D`.
	- Using `virtual` inheritance ensures that the class D is included **only once** as a shared base subobject in the final derived class A.
