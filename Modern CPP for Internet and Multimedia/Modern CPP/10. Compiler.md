### How does C++ work?

C++ is a compiled language, meaning that the code is translated directly into **machine instructions**.  
This process involves several steps — preprocessing, compilation, and linking — which together transform source code into an executable program.

### Why C++, if I’ve learnt Java!

- **Java** runs on a **Virtual Machine (JVM)**, meaning the code is compiled into _bytecode_ interpreted by the JVM, which translates instructions for the hardware.    
- **C++** is compiled directly into _machine code_ for the **target architecture** (x86, ARM, x64, etc.) using the correct toolchain.
- **Performance**: C++ programs run faster since they are executed directly by the hardware.
- **Caution**: Poorly written C++ code can still perform badly.
- **Drawback**: Each target architecture requires **cross-compilation** (separate compilation for each target platform).
- In **TLC systems** (e.g., Gbps routers), efficiency is critical — the software must not be the bottleneck.

### How C++ works

Compilation in C++ follows these stages:
**Source file → Translation unit → Object file → Executable**
1. **Preprocessing**
    - Handles `#include`, `#define`, and other directives.
    - Produces a _pure_ C++ file (translation unit) without preprocessor directives.
2. **Compilation**
    - The compiler converts translation units into **object files**.
3. **Linking**
    - The linker combines object files and libraries to create the **final executable**.

```plaintext
Source file → [Preprocessor] → Translation Unit → [Compiler] → Object File → [Linker] → Executable
```

### **Preprocessor: always before compiler**
- The **preprocessor** evaluates everything that starts with `#` (preprocessor directives) **before** the compiler runs.
- It is **agnostic to C++ syntax**, meaning it just performs text substitution.
- Common use: **macros**, but in modern C++ they should be replaced by `constexpr` whenever possible.

**Example:**

```cpp
#define MAX_HGHT 720
#define AREA(a,b) (a*b)

int maxArea(int a) {
  return AREA(a, MAX_HGHT);
}

int main() {
  int l = MAX_HGHT;
  int a = maxArea(l);
}
```

After preprocessing:

```cpp
int maxArea(int a) {
  return a * 720;
}

int main() {
  int l = 720;
  int a = maxArea(l);
}
```

- The preprocessor removes all macros and replaces them with literal values before compilation.

---

### **Preprocessor: #include**

- The directive `#include` literally **copies** the content of a header file into the source file before compilation.
- If two headers include the same file, the same code is inserted multiple times — causing **duplicate definition errors**.

**Example:**

```cpp
// example.cpp
#include <iostream>
#include "example.h"
#include "example2.h"
int main() {
  std::cout << ex(1) << ex2(2);
}

// example.h
#include "my-fun.h"
inline int ex(int i) { return incr(i+1); }

// my-fun.h
inline int incr(int i) { return i+1; }

// example2.h
#include "my-fun.h"
inline int ex2(int i) { return incr(i+2); }
```

→ **Error:** redefinition of `int incr(int)` because both headers include the same inline function.

---

### **Why is it not compiling?**

- Only `.cpp` files are **compiled**, not headers.
- After preprocessing, the compiler sees a single file (the **translation unit**) that includes all the copied code.
- Multiple inclusions of the same function definitions cause a **compiler error** (`redefinition of function`).

**Simplified preprocessor output:**

```cpp
inline int incr(int i) { return i+1; }
inline int ex(int i) { return incr(i+1); }
inline int incr(int i) { return i+1; }  // duplicated
inline int ex2(int i) { return incr(i+2); }
int main() { std::cout << ex(1) << ex2(2); }
```

→ Error: `redefinition of 'int incr(int)'`.

---

### **Preprocessor: Conditional compilation**

- To prevent multiple inclusions, use **include guards**:

```cpp
// my-fun.h
#ifndef MY_FUN_H
#define MY_FUN_H

inline int incr(int i) { return i+1; }

#endif
```

- When `MY_FUN_H` is defined, the file won’t be included again, preventing redefinitions.
- Always use include guards in every `.h` file.
- Each header must have a **unique guard name**, or compilation conflicts may arise.

---

### **Now it compiles**

When proper include guards are used, the code compiles successfully because each header file is included only once.

**Resulting translation unit:**

```cpp
inline int incr(int i) { return i+1; }
inline int ex(int i) { return incr(i+1); }
inline int ex2(int i) { return incr(i+2); }

int main() {
  std::cout << ex(1) << ex2(2);
}
```

- The compiler now sees a single, valid translation unit with no duplicated definitions.    
- **Important rule:**  
    Each `.cpp` file produces one translation unit, and **only** `.cpp` files are compiled — headers are just included textually.

---

### **Compiler**

The **compiler** performs several key transformations on each translation unit:
1. **Parsing (Linguistic Analysis)**
    - Analyzes syntax and semantics of the C++ code.
2. **Assembly generation**
    - Converts C++ code to **assembly** for a specific CPU instruction set (e.g., ARM, x86, x64).
    - The output is still human-readable ASCII code.
3. **Optimization**
    - Simplifies and optimizes the assembly code (register usage, instruction reordering, removal of redundant code).
    - Optimization levels:
        - `O0`: No optimization (fast compile, slow runtime; used for debugging)
        - `O1`: Removes unused lines (basic optimization)
        - `O2`: Default — minimizes register use, harder to debug
        - `O3`: Maximum optimization, minimal debug visibility
4. **Code generation**
    - Translates assembly into binary **machine code**, creating the **object file** (`.o`).

- Each translation unit is compiled separately into its own object file
- An **object file** (`.o`) contains the compiled binary code for all **defined symbols** (functions, variables, etc.) in that translation unit.
- It may also reference symbols declared but **not defined**, which will be resolved later by the **linker**.

**Advantages:**

- Each translation unit can be compiled independently — only changed files need recompilation.
- Object files can be grouped into **static libraries** (`.a` archives).

**At this stage:**
- Compiler reports **syntax errors** and **type/overload errors** only.
- The code is still **not executable** — missing symbol definitions cause **linker errors** later.

---

### **Compiler example**

**Example of missing symbol definition:**

```cpp
// example.cpp
#include <iostream>
#include "example.h"
int main() { std::cout << ex(1); }

// example.h
#include "my-fun.h"
inline int ex(int i) { return incr(i+1); }

// my-fun.h
int incr(int i);
```

**Output:**

```
undefined reference to `incr(int)'
collect2: error: ld returned 1 exit status
```

- The compiler creates `example.o` but fails to link the program because `incr(int)` is **declared but not defined**.
- The missing definition must be provided in another translation unit (`my-fun.cpp`) for the linker to resolve.

---

When all definitions are provided, the program compiles and links correctly.

**Example:**

```cpp
// example.cpp
#include <iostream>
#include "example.h"
int main() {
  std::cout << ex(1);
}

// example.h
#include "my-fun.h"
inline int ex(int i) {
  return incr(i+1);
}

// my-fun.h
int incr(int i);

// my-fun.cpp
#include "my-fun.h"
int incr(int i) {
  return i+1;
}
```

- `my-fun.cpp` is compiled into **my-fun.o**.
- `example.cpp` is compiled into **example.o**.
- The **linker** combines both object files, resolving the reference to `incr(int)` and creating the **final executable**.

---

### **Linker**

The **linker** produces the **final output** (an executable or a shared library) by combining the object files generated by the compiler.

**Responsibilities:**

1. **Resolve symbol references**:    
    - Replaces references to undefined symbols with their correct memory addresses.
    - These symbols can be defined in other object files or libraries.
2. **Handle library dependencies**:
    - If symbols are defined in external libraries, the linker must be explicitly told where to find them.
3. **Detect linking errors**:
    - **Missing definitions** → function not found.
    - **Duplicate definitions** → function defined more than once.

**Output types:**
- Executable (`.out`, `.exe`)
- Static library (`.a`)
- Shared/dynamic library (`.so`, `.dll`)

---

### **Linker vs Compiler – duplicated definitions**

The compiler and linker detect **different types** of redefinitions:

- **Within one translation unit** → _Compiler error_    
```cpp
    int incr(int i) { return i+1; }
    int incr(int i) { return i+2; }  // same file → compiler error
```

- **Across multiple translation units** → _Linker error_

```cpp
    // my-fun.cpp
    int incr(int i) { return i+1; }
    
    // example.cpp
    int incr(int i) { return i+1; }  // different file → linker error
```


**Typical error message:**

```
my-fun.cpp:3: multiple definition of `incr(int)'
example.cpp:3: first defined here
collect2: error: ld returned 1 exit status
```

**Rule of thumb:**

- Avoid defining the same function in more than one `.cpp` file.    
- Header files should contain **declarations**, not **definitions**.

---

### **Wrapping it up: 1 – Preprocessor**

Example showing the preprocessing phase:

```cpp
// example.cpp
#include "example.h"
int main() { int i = ex(1) + ex(2); }

// example.h
#include "my-fun.h"
inline int ex(int i) { return incr(i+1); }

// my-fun.h
int incr(int i);

// my-fun.cpp
#include "my-fun.h"
int incr(int i) { return i+1; }
```

After preprocessing, the **translation units** are created — each `.cpp` file becomes one translation unit ready for compilation.

---

### **Wrapping it up: 2 – Compiler**

Each **translation unit** is compiled separately into its own **object file**.

**Example:**

```cpp
// translation unit of example.cpp
int incr(int i);
inline int ex(int i) { return incr(i+1); }
int main() { int i = ex(1) + ex(2); }

// translation unit of my-fun.cpp
int incr(int i);
int incr(int i) { return i+1; }
```

**Compilation result:**

```
my-fun.cpp  →  my-fun.o
example.cpp →  example.o
```

At this stage, each `.cpp` file has been transformed into an object file, but the program is still not executable because the files have not yet been linked together.

---

### **Wrapping it up: 3 – Linker**

The **linker** combines all object files and resolves all symbol references to produce the final **executable**.

```
my-fun.o + example.o → executable_example
```

- The linker replaces calls to functions like `incr(int)` in `example.o` with the actual address defined in `my-fun.o`.
- Once all references are resolved, a fully executable binary is produced.
- If any symbols are missing or duplicated, the linker reports an error.

---

### **Static library**

A **static library** is an archive of object files that are **linked at compile time**.

- The executable includes the entire library, making it **self-contained** but **larger** in size.
- If one file changes, the **whole system must be recompiled**.

**Process:**

```
obj1.o + obj2.o + obj3.o → lib1.a   (archiver)
```

The linker then includes all necessary object files from the archive:

```
obj4.o + obj5.o + lib1.a + obj6.o + obj7.o → executable
```

**Advantages:**

- No dependency on external files at runtime.
- Simplifies distribution.

**Disadvantages:**

- Larger executables.
- Harder to update (must recompile if library code changes).

---

### **Shared (or Dynamic) library**

A **shared (dynamic) library** is compiled and linked **at runtime** rather than at compile time.

- Created by the linker (e.g., `.so` in Linux, `.dll` in Windows).
- Can depend on other shared libraries.
- Loaded **once** into memory and shared across programs.

**Advantages:**

- Smaller executables.
- Only the modified library needs recompilation.
- Updates can be distributed independently.

**Example process:**

```
objects → linker → lib1.so, lib2.so
Executable → linked dynamically → loader (runtime)
```

Dynamic linking defers the resolution of symbols until the program starts executing — improving modularity and reducing memory usage.

---

✅ **Summary conclusion**

- **Preprocessor**: expands `#include` and `#define`, producing translation units.
- **Compiler**: converts translation units to object files, checking syntax and semantics.
- **Linker**: combines object files and resolves symbol references to create an executable or library.
- **Static libraries** are compiled into the program, while **dynamic libraries** are linked at runtime.
