# Apache Spark — distributed frameworks

---

## 1. Introduction

**Apache Spark** is an open-source framework for developing and running big data applications on clusters. Devised at UC Berkeley in 2009, it was later donated to the Apache Software Foundation.

Spark is written in Scala and runs on the JVM.

### What Spark provides

| Component | Description |
|---|---|
| **Spark Core** | Unified computing engine: task scheduling, optimization, data abstractions |
| **Programming interface** | Scala, Java, Python, R |
| **Spark SQL** | API for structured data and interactive queries |
| **MLlib** | Machine learning workloads |
| **GraphX** | Graph analytics |
| **Spark Streaming** | Real-time streaming analytics |

## 2. Main features

- **In-memory caching** — Spark keeps intermediate results in memory across rounds. Hadoop writes them to disk instead, which makes Spark significantly faster for iterative algorithms.
- **Fault tolerance** — recovers from node failures without losing computation progress.
- **Optimized scheduling** — transformations are scheduled using DAGs (Directed Acyclic Graphs).

### Where Spark runs

- **Local mode** — driver and executors run as threads on a single machine.
- **Cluster mode** — distributed across a cluster managed by Spark's Standalone manager, YARN, or Mesos.

### Storage

Spark has no built-in storage system. It reads from external sources: HDFS, Amazon S3, Cassandra, Hive, or a relational DBMS.

## 4. Spark application architecture
![[Pasted image 20260310105616.png]]
A Spark application has three main processes.

### 4.1 Driver (a.k.a. master)

The driver is the core of the application. It creates the **SparkContext** (the entry point to Spark's functionality), distributes tasks to executors, and monitors execution.

From Spark 2.0+, **SparkSession** wraps SparkContext and adds more features.

The driver runs code in Java, Python, Scala, or R.

---

### 4.2 Executors (a.k.a. workers)

Executors run the tasks assigned by the driver (compiled to Scala), report status back, and maintain a local cache for persistence.

---

### 4.3 Cluster manager

The cluster manager controls the physical machines and allocates resources. In local mode there's no real cluster — driver and executors are just threads on one machine.

| Mode | Description |
|---|---|
| **Local** | Driver + executors on one machine as threads |
| **Cluster** | Driver + executors can run on different machines |

---

### 4.4 MapReduce tasks in Spark

When an application implements a MapReduce computation, a task typically runs a **map function** on several key-value pairs, or a **reduce function** on several `key → list-of-values` pairs.

1. The code for map/reduce function is executed on one pair at a time
2. Spark tries to assign map/reduce tasks so to minimize data movement and to optimize caching

## 5. Resilient Distributed Dataset (RDD)

An **RDD** (Resilient Distributed Dataset) is Spark's core data abstraction: a collection of elements of the same type, partitioned and distributed across available machines.

- **Coarse-grained transformations** — the interface applies transformations to all the data at once ([Z+12]).
- **Fault-tolerant** — automatic recovery from machine failures.

![[Pasted image 20260310105816.png]]

---

### 5.1 Main characteristics

| Characteristic | Details |
|---|---|
| **Creation** | From stable storage (e.g., HDFS), or from other RDDs via transformations |
| **Immutability** | RDDs are read-only, ensuring consistency in multithreaded execution |
| **Lazy evaluation** | Materialized only when an action is triggered |
| **Lineage tracking** | Spark tracks the full transformation history, so it can recompute partitions after a failure |

---

### 5.2 Partitioning

Partitioning is what makes Spark fast.

- Each RDD is split into **partitions**, distributed across machines.
- The programmer can set the number; otherwise Spark chooses.
- Default: **HashPartitioner** (based on hash codes). Custom partitioners are also supported.
- Rule of thumb: 2x or 3x the number of cores.

How partitioning helps:
- Map tasks run on locally stored partitions, minimizing data movement.
- The `mapPartition` method exposes partitions directly for custom algorithms.
- Aggregation methods like `reduceByKey` exploit partitioning implicitly.

---

### 5.3 RDD operations

#### Transformations

![[Pasted image 20260310110402.png]]

A transformation produces a new RDD. Two types:

| Type | Description | Data movement | Example |
|---|---|---|---|
| **Narrow** | Each input partition maps to at most one output partition, on the same machine | No shuffle — maximum parallelism | `map()` |
| **Wide** | Each input partition may contribute to many output partitions | Shuffle across machines required | `groupByKey()` |

Wide transformations are more expensive since they move data around. Worth keeping in mind when optimizing.

---

#### Actions

An **action** computes a result on an RDD and returns it to the calling program (e.g., `count()`).

RDDs are materialized only when an action runs, not when transformations are defined. If you're benchmarking, make sure the action has actually triggered before measuring.

---

#### Persistence

Persistence saves an RDD in memory after the first action, skipping recomputation on later uses.

| Method | Behavior |
|---|---|
| `cache()` or `persist(StorageLevel.MEMORY_ONLY)` | Stored in RAM. Partitions that don't fit are recomputed when needed. |
| `persist(StorageLevel.MEMORY_AND_DISK)` | Stored in RAM. Partitions that don't fit spill to disk. |

## 6. Implementing MapReduce algorithms in Spark

Spark supports MapReduce but goes well beyond it. The core idea it borrows from functional programming: functions can be passed as arguments.

### Structure of a typical Spark program

1. Spark configuration (create SparkContext or SparkSession).
2. Global variable and data structure definitions (held in driver memory).
3. Read input into one or more RDDs.
4. Implement the MapReduce logic, round by round.

---

### 6.1 Implementing a MapReduce round in Spark


> [!NOTE]- Answer
> We have a RDD $X$ (input *key,value* pairs) that we transform through the **map phase** into an RDD $X'$ (intermediate *key,value* pairs) and then through the **reduce phase** into the output RDD $Y$ (output *key,value* pairs).
> In practice, there might be several intermediate RDDs created by the transformation of $X$ into $Y$
> 
> (maybe, add an image)




#### Map phase

On input RDD **X**, call a Spark map method (narrow transformation), passing the map function as an argument.

#### Reduce phase

On intermediate RDD **X'**:

1. Call a grouping method (wide transformation) to produce `key → list-of-values` pairs.
2. Apply the reduce function via a map method.

Or skip both steps and use a ready-made primitive like `reduceByKey`, which handles grouping and reduction in one optimized call.

## 7. DataFrames and Datasets

RDDs are the low-level, schema-less foundation. The Spark SQL module adds higher abstractions:

| Abstraction | Description | Availability |
|---|---|---|
| **DataFrame** | Distributed collection organized into named columns (similar to a relational table) | All languages |
| **Dataset** | DataFrame with a type-safe, object-oriented interface | Java and Scala only |

This course uses RDDs only.
