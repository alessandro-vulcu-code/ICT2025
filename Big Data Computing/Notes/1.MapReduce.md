## The Big Data Problem

In the early 2000s, a new challenge emerged across many domains: the need to analyze massive amounts of data that existing tools simply could not handle. Datasets were growing to scales like 50 billion web pages amounting to roughly 1,000 TB — far beyond what a single machine could process in any reasonable time. Even algorithms with moderate complexity became unfeasible, and platforms were constrained by limited main memory.

The natural response was to turn to powerful distributed computing systems, which had previously been reserved for specialized scientific applications (physics simulations, weather forecasting, genomics). However, these systems brought their own set of problems: high acquisition and maintenance costs, rapid obsolescence, serious fault-tolerance challenges (more components means more failures), and the need for sophisticated programming skills to effectively exploit parallelism.

## What is MapReduce?

MapReduce was introduced by Google in 2004 as a programming framework designed to make large-scale distributed data processing both practical and accessible. Its key insight was to combine a clean **data-centric programming model** with an implementation that hides all the messy infrastructure details — task allocation, data distribution, fault tolerance, and load balancing — from the developer.

The model draws inspiration from functional programming, specifically the `map` and `reduce` primitives. This leads to two defining properties: algorithms are expressed as data transformations (rather than procedural steps), and the framework can automatically parallelize and distribute the computation without programmer intervention.

## Platforms and Frameworks

MapReduce applications typically run on clusters of commodity hardware (on-premises) or on cloud infrastructure from providers like Amazon AWS or Microsoft Azure — either as Infrastructure as a Service (IaaS), where the user manages the OS and applications, or as Platform as a Service (PaaS), where more of the stack is managed externally.

![[Pasted image 20260225085017.png]]

The underlying infrastructure usually follows a standard cluster architecture: racks of 16–64 compute nodes connected by fast switches (e.g., 10 Gbps Ethernet), sitting on top of a **Distributed File System (DFS)**. The DFS divides files into chunks (typically 64 MB each), replicates them across nodes and racks for fault tolerance, and tracks their locations via replicated master nodes. The two most prominent examples are Google's GFS and the open-source **Hadoop Distributed File System (HDFS)**.

On the software side, **Apache Hadoop** became the most popular MapReduce implementation and spawned an entire ecosystem of tools. **Apache Spark**, covered in depth in courses on the topic, builds on the same ideas but offers a much richer programming environment and significantly better performance. Both use HDFS as their storage layer.

## The MapReduce Computation Model

A MapReduce computation is structured as a sequence of **rounds**. Each round transforms a set of key-value pairs into another set of key-value pairs through two phases:

1. **Map phase**: a user-defined `map` function is applied independently to each input key-value pair, producing zero or more _intermediate_ key-value pairs.
2. **Reduce phase**: the intermediate pairs are grouped by key, and a user-defined `reduce` function is applied to each group (i.e., to the list of values sharing the same key), producing the output pairs for that round.

Between the two phases, a **shuffle** step moves intermediate pairs to the appropriate workers — this is often the most expensive part of a round.

In multi-round computations, the output of one round becomes the input to the next. Additionally, some data can be broadcast as **global variables** accessible to all workers, a feature supported by frameworks like Spark.

The use of key-value pairs may seem like added complexity, but it is essential: keys act as addresses for data and as labels that define groupings during the reduce phase.

## Word Count: A Classic Example

The canonical MapReduce example is **word count**: given a collection of documents, count how many times each word appears across all of them.

- **Input**: each document is a key-value pair `(doc_id, list_of_words)`.
- **Map**: for each document, emit one pair `(word, count)` per distinct word (or one `(word, 1)` per occurrence).
- **Shuffle**: group all pairs by word.
- **Reduce**: for each word, sum the counts to produce the final `(word, total_count)`.

This single-round algorithm is simple and effective, though it may not scale optimally for very large inputs — an issue addressed by more advanced partitioning techniques covered later in the course.

The user program is forked into a master process and several executor processes. 
Master is in charge of:
- assigning map
- reduce tasks to the various executors 
- monitor their status
Input files are read from either the DFS or the master's disk, while output files might be stored on DFS or on the master's disk.

Between the map and reduce phases intermediate key-value pairs are moved from the workers where they where produced to the workers where they must be processed --> **Data shuffle**

## MR specification
A **MapReduce (MR)** algorithm should be specified so that:
- In/Out are clearly defined;
- Sequenceof rounds executed for any given input instance is unambiguously implied by the specification;
- for each round:
	- input, intermediate and output sets of key-value pairs;
	- functions applied in the map and reduce phases.
- Meaningful values (or asymptotic) bounds for the key performance indicators (defined later) can be derived.

> [!ABSTRACT] MapReduce Algorithm: Word Count (Round 1)
> * **Input**: $k$ documents $D_1, D_2, \dots, D_k$ (e.g., $k=4$).
>     * $D_i = (\text{name}, \text{list of words})$
>     * **Key**: name | **Value**: list of words
> * **Output**: $\{ (w, c(w)) : w \text{ is a word occurring in the } D_i\text{'s} \}$
>     * $c(w) = \# \text{occurrences of } w \text{ in the } D_i\text{'s}$
>
> ---
> ### Round 1
>
> #### MapPhase
> For each $D_i$ ($1 \le i \le k$) separately:
> $$D_i \xrightarrow{\text{map function in } D_i} \{ (w, c_i(w)) : w \in D_i, c_i(w) = \# \text{occurrences of } w \text{ in } D_i \}$$
>
> #### ReducePhase
> For each word $w$ separately, let $L_w = \text{list of counts } c_i(w)$ for $i=1 \dots k$ (some may not exist):
> $$(w, L_w) \xrightarrow{\text{reduce function}} (w, \sum_{c_i(w) \in L_w} c_i(w))$$

## Performance
Key performance indicators:
- **Number of rounds R**.
- **Local space $M_L$**: maximum amount of main memory required by a single invocation of a map or reduce function, for storing the input and any data structure needed by the invocation (including possible shared variables). The maximum is taken over all rounds and all invocations in each round
- Aggregate space MA: maximum amount of (disk) space which is occupied by the stored data at the beginning/end of a map or reduce phase. The maximum is taken over all rounds

>[!NOTE] Observations
> * **$R$**: Rough estimate of **running time** under the assumption that **SHUFFLES** dominate the complexity and have comparable costs across different machines. 
> * **$M_L$**: Amount of **MAIN MEMORY** needed at each executor, i.e., at each computing node. 
> * **$M_d$**: Overall amount of **DISK SPACE** needed in the system, i.e., the capacity of the DFS.

> [!abstract] Analysis of Word count
> 
> ### Local Space Complexity ($M_L$)
> * $R: 1$
> * $N_i = \text{\#words in } D_i$ (Hp. 1 word $\in \Theta(1)$ space)
> * $N_{max} = \max \{ N_i : 1 \le i \le k \}$
> * **Map Phase:** $O(N_{max})$ local space
> * **Reduce Phase:** $O(k)$ local space
> 
> $\Rightarrow M_L \in O(\max \{ N_{max}, k \}) = O(N_{max} + k)$
> 
> ---
> 
> ### Aggregate Space Complexity ($M_A$)
> * $N = \sum_{i=1}^{k} N_i$ total number of word occurrences across all documents
> * Space occupied by input pairs: $O(N)$
> * Space occupied by intermediate and output pairs: $O(N)$
> 
> $\Rightarrow M_A \in O(N)$




**Remark**: the trivial solution implied by the observation is not practical for every large inputs *S* for the following reasons:
- Very large main memory at each node is needed;
- No parallelism is exploited;
*S* is at least proportional to in/out size.

> [!info] Design Goals for MapReduce Algorithms
> > [!Question] Note well
> For every problem solvable by a sequential algorithm in space *S*, there exists a 1-round MapReduce algorithm with both $M_L$ and $M_A$ proportional to *S*. Why?
> Assign key zero to all input elements, and use sequential algorithm as **reduce** function
> 
> 1. **Few rounds**: e.g., $R = O(1)$;
> 2. **Sublinear local space**: e.g., $M_L = O(|\text{input}|^\epsilon)$, with $\epsilon < 1$;
> 3. **Linear aggregate space**: i.e., $M_A = O(|\text{input}|)$, or only slightly superlinear;
> 4. **Low complexity** of each map or reduce function.
> 
> ---
> > [!warning] Trade-offs
> > These goals are **conflicting with one another** and, in practice, suitable **trade-offs** among them must be sought.

## Pro and cons of map reduce

| **Category** | **Key Point**                  | **Description**                                                                                                                                                         |
| ------------ | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Pros**     | **Data-centric view**          | Algorithm design focuses on data transformations targeting specific design goals.                                                                                       |
|              | **Usability**                  | The framework transparently handles complex tasks like task allocation, data management, and failure handling, relieving the programmer.                                |
|              | **Portability / Adaptability** | Applications can run on various platforms; the framework optimizes parallelism and minimizes data movement costs.                                                       |
|              | **Cost**                       | Runs on moderately expensive platforms and is widely supported by popular cloud providers.                                                                              |
| **Cons**     | **Performance Measurement**    | Running time is only coarsely captured by $R$. More sophisticated (but less usable) time-performance measures are required.                                             |
|              | **Curse of the last reducer**  | A few slow reducers can delay the entire process. Load balancing among reducers is crucial but difficult.                                                               |
|              | **High-Performance Limits**    | Not suitable for applications requiring tight coupling with underlying architecture (e.g., computational sciences). Super-computers are often required for these cases. |
To attain the stated goal on local space is partitioning:
- **Break the computation in to small tasks**, each processing a **small chunck of data**;
- Chunks can be created through either **deterministic** or **random partitioning**;
- **Maximize independance among tasks to exploit parallelism**.

>[!warning]-  Observation
>While partitioning increases parallelism and reduces the local memory requirements, it might increase the number of rounds and, more rarely, the aggregate space, so **suitable tradeoffs must be sought**

# Deterministic Partitioning
*Lesson 03/03/2026*
**Problem:** given a set *S* of *N* objects with class labels, count how many objects belong to each class.

> [!ABSTRACT] Problem Definition
> **Input**: Set $S$ of $N$ objects represented by pairs $(i, (\gamma_i, o_i))$, for $0 \le i < N$, where $\gamma_i$ is the class of the $i$-th object ($o_i$).
>
> **Output**: The set of pairs $(\gamma, c(\gamma))$ where $\gamma$ is a class labeling some object of $S$ and $c(\gamma)$ is the number of objects of $S$ labeled with $\gamma$.
> 
> *Remark:* we will always assume that $N$ (number of input pairs) is a known value, i.e. a shared variable.

>[!abstract] Class Count in 1 Round (Naive - No Partitioning)
>  In the `map()` function, we create a pair $(\gamma_i, 1)$, where $\gamma_i$ is the class of the object and the value $1$ represents that one object belonging to that class has been processed. 
>   - **Map Phase**: $\forall i \in \{0, \dots, N-1\} \quad (i, (\gamma_i, o_i)) \longmapsto (\gamma_i, 1)$ 
>   - **Reduce Phase**: List of $i$'s from intermediate pairs where $(\gamma_i = \gamma, 1)$. > * $(\gamma, L_\gamma) \longmapsto (\gamma, c(\gamma) = |L_\gamma|)$
>### Analysis
>*(Assuming input pairs take $O(1)$ space)*
>* **$R = 1$** (Number of rounds)
>* **$M_L$ (Local Memory)**:
>	*  Map phase: $O(1)$
>	* Reduce phase: $O(\text{size of largest list}) \implies M_L = O(N)$ in the worst case.
>* **$M_O$ (Aggregate Memory)**: $O(N)$ since there are $O(N)$ input, intermediate, and output pairs.
>
> > [!WARNING] Observation 
>  The algorithm **does not comply** with the design goal: $M_L = O(|input|^\varepsilon)$ with $\varepsilon < 1$.

>[!abstract] Class count in 2 rounds with deterministic partitions
> ### Class count in 2 rounds with deterministic partitions
> ![[Pasted image 20260303170144.png]]
> ![[Pasted image 20260303170205.png]]
> 
>
> ## Round 1
> 
> * **Map phase:** $\forall 0 \le i \le N$ separately: $(i, (\gamma_i, o_i)) \longmapsto (i \pmod{\ell}, \gamma_i)$
> * **Reduce phase:** $\forall 0 \le j < \ell$ separately, let $L_j$ be the list of class labels $\gamma$ from intermediate pairs with key $j$.
>     $(j, L_j) \longmapsto \{(\gamma, c(j, \gamma)) : \gamma \in L_j, c(j, \gamma) = \text{\# occurrences of } \gamma \text{ in } L_j\}$.
>
> ---
>
> ## Round 2
> 
> * **Map phase:** empty
> * **Reduce phase:** $\forall \text{ class } \gamma$ separately, let $L_\gamma = \text{list of } c(j, \gamma)\text{'s from the output pairs of ROUND 1}$, where $j \in \{0, \dots, \ell-1\}$ (some may not exist).
>     $(\gamma, L_\gamma) \longmapsto (\gamma, c(\gamma) = \sum_{c(j, \gamma) \in L_\gamma} c(j, \gamma))$
>
> ---
>
> ## Analysis
> 
> * **$R = 2$** (Total Rounds)
> * **ML (Local Memory):**
>     * **Round 1:**
>         * Map phase: $O(1)$
>         * Reduce phase: $O(N/\ell)$
>     * **Round 2:**
>         * Map phase: $\emptyset$
>         * Reduce phase: $O(\ell)$ *(Note: It would be $O(\ell / \#\text{classes}) \implies O(\ell)$)*
>
> **Total Local Memory:**
> $\implies M_L = O(\max \{ N/\ell, \ell \}) = O(N/\ell + \ell)$
> By fixing $\ell = \sqrt{N}$, we get **$O(\sqrt{N})$**.
>
> > [!IMPORTANT] 
> > This is $M_L$ because we may process ROUND 1 & 2 in parallel.
>
> * **MA (Aggregate Memory):** $O(N)$ since there are $O(N)$ input, intermediate, and output pairs in each of the 2 rounds, and pairs take $O(1)$ space each.
>
> **Conclusion:** This solution meets all design goals.

We can make some observations:
- Deterministic partitioning is attained through a sort of **deterministic hash function**, which uses explicit features, if available, (e.g., the integer key i) to evenly subdivide the pairs into groups.
- The choice of $\ell = \sqrt{N}$ partitions provides an **example of a simple tradeoff between local space and number of rounds.**
- If more **stringent bounds on the local space** are imposed, different partitionings may be needed, yielding **different round-space tradeoffs**. One of the exercises will explore this.

In practice, the number of partitions is fixed as a multiple of the number of available workers, as long as local space is not an issue.

## Random partitioning
Consider the class count problem, but assume that the input pairs are provided without the integer keys in $[0, N)$.

> [!ABSTRACT] Problem Definition
> **Input**: Set $S$ of $N$ objects represented by pairs $(\gamma_i, o_i)$, for $0 \le i < N$, where $\gamma_i$ is the class of the $i$-th object $(o_i)$.
>**Output**: The set of pairs $(\gamma, c(\gamma))$ where $\gamma$ is a class labeling some object of $S$ and $c(\gamma)$ is the number of objects of $S$ labeled with $\gamma$.


> [!abstract] Class count in 2 rounds with random partitions (example, $l = 4$ partitions)
> ![[Pasted image 20260303172317.png]]
> ![[Pasted image 20260303172328.png]]
> ### ROUND 1:
> * **Map phase**: $\forall$ input pair separately $(\gamma_i, o_i) \longmapsto (x, \gamma_i)$ 
>   $x = \text{random integer in } [0, \ell) \text{ with uniform distribution}$
> * **Reduce phase**: $\forall x \in [0, \ell)$ separately, let $L_x = \text{list of class labels } \gamma \text{ from}$ $\text{intermediate pairs with key } x. (x, L_x) \longmapsto \{(\gamma, c(x, \gamma)) : \gamma \in L_x, c(x, \gamma) = \# \text{occur.}$ $\text{of } \gamma \text{ in } L_x \}.$
>  
> ---
> 
> ### ROUND 2:
>* **Map phase**: $\emptyset$
>* **Reduce phase**: $\forall$ class label $\gamma$ separately let $L_\gamma = \text{list of } c(x, \gamma) \text{ from}$
> 	$\text{output pairs of round 1}, x \in [0, \ell) \text{ (some may not exist)}$ $(\gamma, L_\gamma) \longmapsto (\gamma, c(\gamma) = \sum_{c(x, \gamma) \in L_\gamma} c(x, \gamma)$
>### Analysis: 
>$m_x = \text{number of intermediate pairs in Round 1 with key } x$ $m = \max \{m_x : 0 \le x < \ell\}$ $R = 2$ $M_L : \text{ Round 1 } \begin{cases} \text{Map phase: } O(1) \\ \text{Reduce phase: } O(m) \end{cases} \implies M_L = O(m + \ell)$ $M_L : \text{ Round 2 } \begin{cases} \text{Map phase: } \emptyset \\ \text{Reduce phase: } O(\ell) \end{cases}$ $M_A: O(N), \text{ same argument as before}$ 
>
>Deterministic partitioning: $M_L = O(N/\ell + \ell)$ 
>Random partitioning: $M_L = O(m + \ell)$ 

>[!question]- How large can $m$ be?
> >[!warning] Theorem
> >Fix $\ell = \sqrt{N}$ and suppose that in Round 1 the keys assigned to intermediate pairs independently and with uniform probability from $[0, \sqrt{N})$. Then, with probability at least $1 - 1/N^5$
> >$$m = O \left( \frac{N}{\ell} \right) = O \left( \sqrt{N} \right).$$
>  
>Based on the theorem (which we will prove shortly) and on the previous analysis, by setting $\ell = \sqrt{N}$ we get
> $$M_L = O \left( \frac{N}{\ell} \right) = O \left( \sqrt{N} \right)$$
> with probability at least $1 - 1/N^5$ (*very close to 1*, for large $N$).
> **N.B.**: This is an example of **probabilistic analysis**, as opposed to more traditional worst-case analysis.

## Observations on partitioning
- **Deterministic partitioning**: applicable whenever input pairs contain pieces of data which can be mapped into partition indices that ensure a sufficiently even partitioning of the pairs.
- **Random partitioning**: always applicable, but to ensure a sufficiently even partitioning, the expected size of each partition should not be too small, and a good random generator must be used.
