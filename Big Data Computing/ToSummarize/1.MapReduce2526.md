## Slide 2 — Motivating scenario

Main reasons why MapReduce was introduced in the early 2000's.

- There was an increasing need to analyze large amounts of data in a wide spectrum of domains.
- Big data processing required high storage and compute capabilities often beyond those of available tools and commonly used platforms
- Supercomputers, typically used for scientific computing, were unsuited for a number of reasons:
  - High costs (millions/billions euros) to buy and maintain them
  - Sophisticated programming skills needed to exploit their potential
  - Crucial low-level issues to be addressed by the user: fault tolerance (see next slide), task allocation, data distribution) → *application*
  - Fast obsolescence
  - Aim for *extreme* performance, often not required by typical big data applications

## Slide 3 — Mean-Time Between Failures (MTBF)

*(Pagina scritta a mano)*

Consider a system of N components $C_1, C_2, \ldots, C_N$ that at each time $t$ may fail independently. Let

$$p = \text{Prob}(C_i \text{ fails at time } t) \quad \text{for any } i \text{ and } t$$

$\Rightarrow \text{Prob}(\exists C_i \text{ that fails at time } t) = 1 - (1-p)^N$

Let $X = $ # time units before the next failure occurs.

Since the components fail independently, $X$ has a **GEOMETRIC DISTRIBUTION**

$$E[X] = \frac{1}{1-(1-p)^N} \xrightarrow{N \to +\infty} 1$$

## Slide 12 — Distributed File System (DFS)

In a big data applications, file containing the data to be analyzed might be too big to reside in one compute node.

Thus, it is convenient, to store the files in a Distributed File System across several compute nodes.

- Files divided into *chunks* (e.g., 64MB per chunk).
- Each chunk replicated (e.g., 2x o 3x) with replicas in different nodes to ensure fault-tolerance.
- Examples: Google File System (GFS); Hadoop Distributed File System (HDFS)

## Slide 15 — MapReduce computation

A MapReduce computation can be viewed as a **sequence of rounds**.

A **round** transforms a set of key-value pairs into another set of key-value pairs (*data-centric view* !), through the following two phases

- **Map phase:** for each input key-value pair separately, a user-specified map function is applied to the pair and produces $\geq 0$ other key-value pairs, sometimes called intermediate pairs.
- **SHUFFLE:** intermediate pairs are grouped by key, by creating, for each key $k$, a list $L_k$ of values of intermediate pairs with key $k$.
- **Reduce phase:** for each key $k$ separately, a user-specified reduce function is applied to $(k, L_k)$ which produces $\geq 0$ key-value pairs, which is the output of the round.

**Terminology:** the application of the reduce function to a pair $(k, L_k)$ is referred to as **reducer**.

## Slide 18 — One round: execution on a distributed platform

- The user program is forked into a master process and several executor processes. The master is in charge of assigning map and reduce tasks to the various executors, and to monitor their status (idle, in-progress, completed).
- Input files are read from either the Distributed File System or the master's disk, while intermediate data are stored on the executors' local memories/disks.
- Output files (if any) might be stored either on a Distributed File System or on the master's disk.
- **Map phase:** each executor is assigned a subset of input pairs and applies the map function to them sequentially, one at a time.
- **Shuffle:** the system collects the intermediate pairs from the executors' local spaces and groups them by key.
- **Reduce phase:** each executor is assigned a subset of $(k, L_k)$ pairs, and applies the reduce function to them sequentially, one at a time.

## Slide 21 — Why key-value pairs?

The use of key-value pairs in MapReduce seems an unnecessary complication, and one might be tempted to regard individual data items simply as *objects* belonging to some domain, without imposing a distinction between keys and values.

**Justification.** MapReduce is data-centric and focuses on data trasformations which are independent of where data actually reside. The keys are needed as **addresses** to reach the objects, and as **labels** to define the groups in the reduce phases.

**Practical considerations.**

- One should choose the key-value representations in the most convenient way. The domains for key and values may change from one round to another.
- Programming frameworks such as Spark, while containing explicit provisions for handling key-value pairs, allow also to manage data without the use of keys. In this case, internal addresses/labels, not explicitly visible to the programmer, are used.

## Slide 22 — Specification of a MapReduce algorithm

A *MapReduce (MR) algorithm* should be specified so that

- The input and output of the algorithm is clearly defined
- The sequence of rounds executed for any given input instance is unambiguously implied by the specification
- For each round the following aspects are clear
  - input, intermediate and output sets of key-value pairs
  - functions applied in the map and reduce phases.
- Meaningful values (or asymptotic) bounds for the key performance indicators (defined later) can be derived.

---

## Slide 23 — Pseudocode style

To specify a MR algorithm with a fixed number of rounds $R$, we will use the following style:

**Input:** description of the input as set of key-value pairs
**Output:** description of the output as set of key-value pairs
**Round 1:**
- *Map phase:* description of the function applied to each key-value pair
- *Reduce phase:* description of the function applied to each group of key-value pairs with the same key

**Round 2, 3, …, R:** similarly

Observation: *for simplicity, we sometime provide a high-level description of a round, which, however, must enable a straightforward yet tedious derivation of the Map and Reduce phases.*

## Slide 24 — Example: Word count (scritta a mano)

**Input:** $k$ documents $D_1, D_2, \ldots, D_k$, where

$$D_i = (\underbrace{\text{name}}_{\text{key}}, \underbrace{\text{list of values}}_{\text{value}})$$

**Output:** $\{(w, c(w)) : w \text{ is a word occurring in the } D_i\text{'s},\ c(w) = \#\text{occurrences of } w \text{ in the } D_i\text{'s}\}$

---

## Slide 25 — Word count: Round 1 (scritta a mano)

**Round 1**

**Map Phase:** for each $D_i$, $1 \leq i \leq k$, separately

$$D_i \to \{(w, c_i(w)) : w \in D_i,\ c_i(w) = \#\text{occurrences of } w \text{ in } D_i\}$$
↑ *map function*

**Reduce Phase:** for each word $w$ separately, let

$$L_w = \text{list of } c_i(w) \quad i=1,2,\ldots,k \quad (\text{some may not exist})$$

$$(w, L_w) \to (w,\ c(w) = \sum_{c_i(w) \in L_w} c_i(w))$$
↑ *reduce function* ↑ *output pair*

## Slide 27 — Performance analysis of a MapReduce algorithm

The analysis of an MR algorithm aims at estimating the following key performance indicators:

- **Number of rounds $R$.**

- **Local space $M_L$:** *maximum amount of main memory required by a single invocation of a map or reduce function*, for storing the input and any data structure needed by the invocation (including possible shared variables). *The maximum is taken over all rounds and all invocations in each round.*

- **Aggregate space $M_A$:** *maximum amount of (disk) space which is occupied by the stored data at the beginning/end of a map or reduce phase. The maximum is taken over all rounds.*

---

## Slide 28 — Observations (scritta a mano)

* $R$: rough estimate of RUNNING TIME, under the assumption that all rounds have approximately the same complexity (e.g. dominated by the shuffle)
* $M_L$: amount of MAIN MEMORY needed at each executor, hence at each compute node
* $M_A$: overall amount of DISK SPACE needed in the system

---

## Slide 29 — Analysis of Word Count (scritta a mano)

**Analysis of Word Count**

* $R = 1$

* $M_L$: (Hp: 1 word $\equiv O(1)$ space)
  - $N_i = $ # words in $D_i$
  - $N_{\max} = \max\{N_i : 1 \leq i \leq k\}$
  - Map Phase: $M_L = O(N_{\max})$
  - Reduce Phase: $M_L = O(k)$
  - $\Rightarrow M_L = O(\max\{N_{\max}, k\}) = O(N_{\max} + k)$

---

## Slide 30 — Analysis of Word Count — $M_A$ (scritta a mano)

* $M_A$:

$$N = \sum_{i=1}^{k} N_i \equiv \text{total number of occurrences of all words aggregated over all documents}$$

- Space required by input pairs: $O(N)$
- Space required by intermediate pairs: $O(N)$
- Space required by output pairs: $O(N)$

$$\Rightarrow M_A = O(N)$$

## Slide 32 — Design goals for MapReduce algorithms

> **Important observation**
>
> For every problem solvable by a sequential algorithm in space $S$ there exists a 1-round MapReduce algorithm with both $M_L$ and $M_A$ proportional to $S$. Justify this observation.

*(risposta scritta a mano sul lucido):*

Assign key 0 to all input elements, and use the sequential algorithm as reduce function

**Remark:** the trivial solution implied by the observation is not practical for very large inputs $\mathcal{S}$ for the following reasons:

- Very large main memory at each node is needed. Since $S \geq$ input size
- No parallelism is exploited.

---

## Slide 33 — Design goals for MapReduce algorithms

> **Design Goals for MapReduce Algorithms**
>
> 1. Few rounds (e.g., $R = O(1)$);
> 2. Sublinear local space (e.g., $M_L = O(|\text{input}|^\epsilon)$, with $\epsilon < 1$);
> 3. Linear aggregate space (i.e., $M_A = O(|\text{input}|)$), or only slightly superlinear;
> 4. Low complexity of each map or reduce function.

---

## Slide 34 — Design goals for MapReduce algorithms (scritta a mano)

**1, 4:** AIM AT TIME EFFICIENCY
- $1 \Rightarrow$ low communication/synchronization costs
- $4 \Rightarrow$ low computation costs

**2, 3:** AIM AT SPACE EFFICIENCY
- $2 \Rightarrow$ low main memory usage $\}$ aim at feasibility
- $3 \Rightarrow$ low overall space usage $\}$ of computation on
  (e.g., low data replication) $\}$ commodity HW

---

## Slide 35 — Osservazione (scritta a mano)

**Observation:** the above goals are somewhat conflicting and, in practice, suitable tradeoffs must be sought.

## Slide 36 — Pros and cons of MapReduce

Why is MapReduce **suitable** for big data processing?

- **Data-centric view.** Algorithm design focuses on data transformations targeting the above design goals.
- **Usability.** The programmer is lifted from performing crucial but difficult activities such as allocation of tasks to workers, data management, and handling of failures, which are instead dealt with transparently by the supporting framework.
- **Portability/Adaptability.** Applications can run on different platforms and the supporting framework will do best effort to exploit parallelism and minimize data movement costs.
- **Cost.** MapReduce applications can be run on moderately expensive platforms, and many popular cloud providers support their execution.

---

## Slide 37 — Pros and cons of MapReduce

What are the **main drawbacks** of MapReduce?

- **Running time is only coarsely captured by $R$.** More sophisticated (yet, less usable) time-performance measures should be used.
- **Curse of the last reducer.** In some cases, one or a few reducers may be much slower than the others, thus delaying the end of the round. Algorithm designers should aim at balancing the load (if at all possible) among reducers.
- **MapReduce is not suitable for applications that require very high performance** and a tight coupling with the underlying architecture (e.g., from computational sciences).

## Slide 38 — Partitioning

> **Partitioning**
>
> A typical approach to attain the stated goal on local space is to
>
> - Break the computation into small tasks, each processing a small chunk of data (e.g., applications of map/reduce functions)
> - Chunks (e.g., for reduce functions) can be created through either deterministic or random partitioning
> - Maximize independence among tasks to exploit parallelism

**Observation.** While partitioning increases parallelism and reduces the local memory requirements, it might increase the number of rounds and, more rarely, the aggregate space.

$\Rightarrow$ Suitable tradeoffs must be sought.

## Slide 40 — Class count

**Problem:** given a set $S$ of $N$ objects with class labels, count how many objects belong to each class.

More precisely:

**Input:** Set $S$ of $N$ objects represented by pairs $(i, (\gamma_i, o_i))$, for $0 \leq i < N$, where $\gamma_i$ is the class of the $i$-th object ($o_i$).

**Output:** The set of pairs $(\gamma, c(\gamma))$ where $\gamma$ is a class labeling some object of $S$ and $c(\gamma)$ is the number of objects of $S$ labeled with $\gamma$.

Remark: *we will always assume that $N$ (the number of input pairs) is a known value, i.e., a shared variable.*

---

## Slide 41 — Class count in 1 round (naive - no partitioning) (scritta a mano)

**Map Phase:** $\forall i=0\ldots N-1$: $(i, (\gamma_i, o_i)) \to (\gamma_i, 1)$

**Reduce Phase:** For each class $\gamma$

$$L_\gamma = \text{list of } 1\text{'s from intermediate pairs } (\gamma_i = \gamma, 1)$$

$$(\gamma, L_\gamma) \to (\gamma,\ c(\gamma) = |L_\gamma|)$$

**Analysis** (assume input pairs take $O(1)$ space)

$R = 1$

---

## Slide 42 — Class count: analisi (scritta a mano)

$M_L$:
- Map Phase: $O(1)$
- Reduce Phase: $O(\text{size of biggest list})$
- $\Rightarrow M_L = O(N)$ in the worst case

$M_A$: $O(N)$ since there are $O(N)$ input, intermediate and output pairs

**Observation:** The algorithm does not comply with the design goal:
$$M_L = O(|\text{input}|^\epsilon) \quad \epsilon < 1$$

## Slide 46 — Class count in 2 rounds with deterministic partitions (scritta a mano)

**Round 1**

**Map Phase:** $\forall 0 \leq i < N$ separately: $(i, (\gamma_i, o_i)) \to (i \bmod \ell,\ \gamma_i)$

**Reduce Phase:** $\forall 0 \leq j < \ell$ separately, let

$$L_j = \text{list of class labels } \gamma \text{ from intermediate pairs with key } j$$

$$(j, L_j) \to \{(\gamma, c(j,\gamma)) : \gamma \in L_j,\ c(j,\gamma) = \#\text{occurrences of } \gamma \text{ in } L_j\}$$

---

## Slide 47 — Class count: Round 2 (scritta a mano)

**Round 2**

**Map Phase:** empty

**Reduce Phase:** $\forall$ class $\gamma$ separately, let

$$L_\gamma = \text{list of } c(j,\gamma)\text{'s from output pairs of Round 1},\ 0 \leq j < \ell \quad (\text{some may not exist})$$

$$(\gamma, L_\gamma) \to \left(\gamma,\ c(\gamma) = \sum_{c(j,\gamma) \in L_\gamma} c(j,\gamma)\right)$$

---

## Slide 48 — Analysis (scritta a mano)

**Analysis**

$R = 2$

$M_L$:
- Round 1:
  - Map Phase: $O(1)$
  - Reduce Phase: $O(N/\ell)$
- Round 2:
  - Map Phase: —
  - Reduce Phase: $O(\ell)$

$$\Rightarrow M_L = O(\max\{N/\ell,\ \ell\}) = O(N/\ell + \ell)$$

---

## Slide 49 — Analisi: $\ell = \sqrt{N}$ (scritta a mano)

By fixing $\ell = \sqrt{N}$ we get $M_L = O(\sqrt{N})$

$M_A$: $O(N)$ since there are $O(N)$ input, intermediate and output pairs in each of the 2 rounds, and pairs take $O(1)$ space each.

$\Rightarrow$ **THIS SOLUTION MEETS ALL DESIGN GOALS**

---

## Slide 50 — Observations

- Deterministic partitioning is attained through a sort of deterministic hash function, which uses explicit features, if available, (e.g., the integer key $i$) to evenly subdivide the pairs into groups.
- The choice of $\ell = \sqrt{N}$ partitions (which we will often make) provides an example of a simple tradeoff between local space and number of rounds.
- If more stringent bounds on the local space are imposed, different partitionings may be needed, yielding different round-space tradeoffs. One of the exercises will explore this.
- In practice, the number of partitions is fixed as a multiple of the number of available workers, as long as local space is not an issue.

## Slide 60 — How large can $m$ be?

> **Theorem**
>
> Fix $\ell = \sqrt{N}$ and suppose that in Round 1 the keys assigned to intermediate pairs independently and with uniform probability from $[0, \sqrt{N})$. Then, with probability at least $1 - 1/N^5$
>
> $$m = O\!\left(\frac{N}{\ell}\right) = O\!\left(\sqrt{N}\right).$$

Based on the theorem (which we will prove shortly) and on the previous analysis, by setting $\ell = \sqrt{N}$ we get

$$M_L = \underbrace{O\!\left(\frac{N}{\ell}\right)}_{} + \ell = O\!\left(\sqrt{N}\right)$$

*(annotazione a mano:* $M_L = O(m+\ell)$*)*

with probability at least $1 - 1/N^5$ (*very close to 1, for large N*).

**N.B.:** This is an example of probabilistic analysis, as opposed to more traditional worst-case analysis.

## Slide 61 — Review of useful probabilistic tools

> **Union bound**
>
> Given a countable set of events $E_1, E_2, \ldots, E_r$, we have:
>
> $$\Pr\!\left(\bigcup_{i=1}^{r} E_i\right) \leq \sum_{i=1}^{r} \Pr(E_i).$$

> **Markov's inequality**
>
> Let $X$ be a nonnegative random variable. For any $a > 0$ we have:
>
> $$\Pr(X \geq a) \leq \frac{E[X]}{a}$$

---

## Slide 62 — Useful probabilistic tools

> **Chernoff bound**
>
> Let $X_1, X_2, \ldots, X_n$ be $n$ i.i.d. Bernoulli random variables, with $\Pr(X_i = 1) = p$, for each $1 \leq i \leq n$. Thus, $X = \sum_{i=1}^{n} X_i$ is a Binomial$(n, p)$ random variable. Let $\mu = E[X] = n \cdot p$. For every $\delta_1 \geq 6$ and $\delta_2 \in (0,1)$ we have:
>
> (a) $\Pr(X \geq \delta_1 \mu) \leq 2^{-\delta_1 \mu}$
>
> (b) $\Pr(X \leq (1-\delta_2)\mu) \leq 2^{-\delta_2^2 \mu/2}$

## Slide 64 — Proof of theorem (scritta a mano)

Assume $N \geq 16$ (otherwise theorem is straightforward)

Focus on an arbitrary $x \in [0, \sqrt{N})$ and call $m_x$ = # intermediate pairs that in R1 receive key $x$.

For $0 \leq i < N$ define:

$$Y_i = \begin{cases} 1 & \text{if } (\gamma_i, o_i) \to (x, \gamma_i) \\ 0 & \text{else} \end{cases}$$

$Y_i$ is a Bernoulli random variable with $P_r(Y_i = 1) = \frac{1}{\sqrt{N}}$

$$\Rightarrow m_x = \sum_{i=0}^{N-1} Y_i \Rightarrow m_x \text{ is Binomial}\!\left(N,\ \frac{1}{\sqrt{N}}\right)$$

$$\Rightarrow E[m_x] = \sqrt{N}$$

---

## Slide 65 — Proof of theorem (cont.) (scritta a mano)

By the Chernoff Bound (a) we have that

$$P_r(m_x \geq 6\sqrt{N}) \leq 2^{-6\sqrt{N}}$$

Now, for $N \geq 16$ we have $\sqrt{N} \geq \log_2 N$

$$\Rightarrow 2^{-6\sqrt{N}} \leq 2^{-6\log_2 N} = (1/2)^{\log_2(N^6)} = (1/N)^6$$

$$\Rightarrow P_r(m_x \geq 6\sqrt{N}) \leq (1/N)^6$$

We now extend the bound to $m = \max\{m_x : x \in [0,\sqrt{N})\}$

Define the event $E_x =$ "$m_x \geq 6\sqrt{N}$"

$$P_r(m \geq 6\sqrt{N}) = P_r(E_0 \cup E_1 \cup \cdots \cup E_{\sqrt{N}-1})$$

---

## Slide 66 — Proof of theorem (fine) (scritta a mano)

(by the union bound) $\leq \sqrt{N} \cdot P_r(E_x)$ for any $x$

$$\leq \sqrt{N} \cdot \frac{1}{N^6} \leq \frac{1}{N^5}$$

Hence the probability $P_r(m \geq 6\sqrt{N}) \leq 1/N^5$

$$\Rightarrow P_r(m \leq 6\sqrt{N}) \geq 1 - 1/N^5$$

$\Rightarrow$ WITH VERY HIGH PROBABILITY $m \leq 6\sqrt{N}$, that is $m = O(\sqrt{N})$ $\square$

## Slide 67 — Conclusione (scritta a mano)

**CONCLUSION:** If we distribute $N$ objects at random among $\ell$ partitions, and $N/\ell$ is sufficiently large, then with high probability no partition receives an excessive number of objects.

## Slide 68 — Observations on partitioning

- **Deterministic partitioning:** applicable whenever input pairs contain pieces of data which can be mapped into partition indices that ensure a sufficiently even partitioning of the pairs.
- **Random partitioning:** always applicable, but to ensure a sufficiently even partitioning, the expected size of each partition should not be too small, and a good random generator must be used.
